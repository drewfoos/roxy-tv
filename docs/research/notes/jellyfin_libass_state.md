# Jellyfin ASS/SSA (libass) Subtitle Rendering: State as of October 2026 (server + every official client + notable third-party clients)

Research date: 2026-10-13. Version landscape at research time: Jellyfin server 12.0 (released 2026-09-07; versioning dropped the "10." prefix, so 12.0 is what would have been 10.12.0), Jellyfin Android TV stable v0.19.10 (2026-08-16) with v0.20.0-beta.1/2/3 (Sep 2026) in beta, Jellyfin Media Player (now "Jellyfin Desktop") v1.12.0 stable with a v2.0.0 pre-release. Anything from 2023-2025 is marked historical below.

Terminology used throughout:
- "Native libass" = the client itself renders the ASS script (positioning, fonts, karaoke, \move, etc.) using libass or a libass derivative, on-device, with no video transcode.
- "Burn-in" = the Jellyfin server transcodes the video and hardcodes subtitles into the picture via jellyfin-ffmpeg's `subtitles`/`ass` filter (which itself uses libass server-side). Typesetting fidelity is then determined by server-side font availability.
- "Plain-text degrade" = the client receives ASS/SSA (or a converted copy) but renders only the text, dropping styles/positions.

---

## Key Question 1: Which Jellyfin clients render ASS natively (full libass with embedded fonts) vs. fall back to server burn-in vs. degrade to plain text?

### Takeaway
As of October 2026, the only official Jellyfin clients with full native libass rendering are the mpv-based desktop app (Jellyfin Media Player / Jellyfin Desktop) and Jellyfin for Kodi / JellyCon (via Kodi's own libass-based player); Jellyfin Web uses a WebAssembly libass fork (libass-wasm/SubtitlesOctopus) and is the next-best; Android TV has an experimental, disabled-by-default libass-android renderer only in the 0.20.0 betas; every other official client (Android mobile, Swiftfin, Roku, webOS, Tizen) either forces server burn-in or degrades styling. Third-party mpv-based clients (Streamyfin, Findroid, Wholphin, JellyPlay) and Infuse provide native rendering.

### Cited Findings

**Server-side capability matrix (what the server knows about ASS)**
- Jellyfin's official codec-support docs classify ASS/SSA as "Formatted Text" and list container support: MKV = supported, MP4 = not, TS = not, AVI = "depends on device and/or settings". The page says that if subtitles need transcoding "they can be converted into another format that is supported, or burned into the video", calls burn-in "the most intensive method of transcoding", and notes "Text-based subtitle formats require fonts to render properly." It does not give a per-client ASS matrix. — [Jellyfin docs: Codec Support](https://jellyfin.org/docs/general/clients/codec-support/)

**Jellyfin Web (browser) — libass via WebAssembly (libass-wasm / JavascriptSubtitlesOctopus fork)**
- jellyfin-web renders ASS/SSA with `@jellyfin/libass-wasm`, Jellyfin's fork of JavascriptSubtitlesOctopus (libass compiled to WebAssembly). The error source in a 2024-25 bug was `subtitles-octopus-worker.js`, "a WebAssembly build of libass". — [jellyfin-web issue #6299](https://github.com/jellyfin/jellyfin-web/issues/6299); [npm @jellyfin/libass-wasm](https://www.npmjs.com/package/@jellyfin/libass-wasm)
- Jellyfin Web has a per-user "burn subtitles" setting; a forum user fixed ASS display by choosing "burn in all complex formats", and the reply says that option "has to be selected per client" and "there's currently no way to make this the default for all clients" (March 2024, historical). — [Jellyfin forum: subtitle does not display correctly](https://forum.jellyfin.org/t-subtitle-does-not-display-correctly)
- In Sept 2026 (Jellyfin 12.0, Firefox 155) a reporter saw ASS not rendering with exceptions inside `libass-wasm`, "Subtitles show up just fine in Chrome"; the reporter used "native" subtitle rendering since "Auto" did not work reliably in Firefox. The crash was traced to the third-party "Jellyfin Enhanced" plugin interacting with Jellyfin 12; updating the plugin resolved it; closed completed 2026-09-13. Confirms libass-wasm is still the renderer in 12.0. — [jellyfin-web issue #8479](https://github.com/jellyfin/jellyfin-web/issues/8479)
- Historical (2020): jellyfin-web issue "Provide an alternative to JavascriptSubtitlesOctopus" explains SubtitlesOctopus "is ported from libass and relies on font files" and that this "breaks the display of CJK characters since Jellyfin doesn't provide any CJK fonts by default". — [jellyfin-web issue #1670](https://github.com/jellyfin/jellyfin-web/issues/1670)
- Historical: Safari could not render ASS subtitles (jellyfin-web issue). — [jellyfin-web issue #3687](https://github.com/jellyfin/jellyfin-web/issues/3687)
- JASSUB (the successor to SubtitlesOctopus) has NOT been adopted by jellyfin-web; the only JASSUB adoption found was in an unrelated project's PR which calls JASSUB "the successor to the SubtitlesOctopus fork jellyfin-web still uses". — [photon-server PR #321](https://github.com/olivertgwalton/photon-server/pull/321)
- Third-party aggregator claims Jellyfin Web 10.11.6 "added default font fallback" (unverified against official notes). — [releasebot.io jellyfin-web](https://releasebot.io/updates/jellyfin/jellyfin-web)

**Jellyfin Media Player / Jellyfin Desktop (Windows/macOS/Linux) — native libass via mpv**
- The README says the client is "built with Qt WebEngine and libmpv"; users can supply an `mpv.conf`. Project is now named "Jellyfin Desktop". — [jellyfin-media-player README](https://github.com/jellyfin/jellyfin-media-player)
- Releases: v1.12.0 (20 Mar, marked Latest; year inferred 2025) is a bugfix release; v2.0.0 (14 Dec, pre-release; year inferred 2025) "Renames the app to Jellyfin Desktop and upgrades to Qt 6" and adds "MpvQt library dependency". v1.10.0 "Update mpv version to latest git version", "Improve customization for subtitles". No release note mentions libass by name (it is implicit via mpv). — [jellyfin-media-player releases](https://github.com/jellyfin/jellyfin-media-player/releases)
- Forum consensus: "Jellyfin Media Player and MPV Shim are described as handling ASS best because both use MPV as their player." — [Jellyfin forum: ASS subtitles not supported](https://forum.jellyfin.org/t-ass-subtitles-not-supported?pid=15310)
- In the 2024-25 libass-wasm font bug, a Jellyfin member noted "Jellyfin Media Player was unaffected" while web/Android/Roku were. — [jellyfin-web issue #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)

**Jellyfin Android (mobile) — ExoPlayer/Media3; no libass; degrades or burns in**
- Issue #1833 "Regarding native ASS subtitle playback" (opened 2025-10-31): the Android client "relies on Media3's built-in ExoPlayer" which "does not handle ASS subtitles well. Enabling 'ASS compatibility' strips styling, and disabling it makes the server transcode the video." Proposed libass integration or an mpv backend. On 2026-05-05 maintainer nielsvanvelzen said: "Support for ASS subtitles is already developed and going to be released as experimental option" in the next TV app version, and "We will port it to the mobile app later as well." Mobile ASS rendering is not implemented as of that date. — [jellyfin-android issue #1833](https://github.com/jellyfin/jellyfin-android/issues/1833)
- The mobile app has an "Allow SSA/ASS subtitles in direct play" option (the TV app historically lacked it). — [jellyfin-androidtv issue #2875](https://github.com/jellyfin/jellyfin-androidtv/issues/2875)
- Historical (Jan 2025) moderator note: the Android phone app "does have some form of support for ASS subs as long as you use the native ExoPlayer" (i.e., partial, unstyled). — [Jellyfin forum: Android vs Android TV subtitle support](https://forum.jellyfin.org/t-android-vs-android-tv-subtitle-support)
- Workaround: the Android app can hand off to external players (MPV, VLC, MX Player) for proper ASS. — [Jellyfin forum: ASS subtitles not supported](https://forum.jellyfin.org/t-ass-subtitles-not-supported?pid=18157)
- Historical: external .ass files sometimes not recognized by the mobile app (confirmed bug, issue #1291). — [jellyfin-android issue #1291](https://github.com/jellyfin/jellyfin-android/issues/1291)

**Jellyfin Android TV — forced burn-in in stable 0.19.x; experimental libass in 0.20 betas** (see Key Question 2 for full detail)
- Maintainer (2026-04-04, app 0.19.7 / server 10.11.6): the app "relies on the server to transcode ASS subtitles". — [jellyfin-androidtv issue #5507](https://github.com/jellyfin/jellyfin-androidtv/issues/5507)
- v0.20.0-beta.1 (2026-09-08): "Support Advanced SubStation Alpha direct play" #5121 — experimental, disabled by default, developer-settings toggle. — [v0.20.0-beta.1 release](https://github.com/jellyfin/jellyfin-androidtv/releases/tag/v0.20.0-beta.1); [PR #5121](https://github.com/jellyfin/jellyfin-androidtv/pull/5121)

**Jellyfin for Kodi / JellyCon — native via Kodi's player (libass)**
- A 2026 comparison lists Jellyfin for Kodi v2.2.0 (2026-09-17) and JellyCon v1.0.2 (2026-07-06); "Both use Kodi's own player." — [Swiftly: Jellyfin Android TV clients compared (2026)](https://swiftlyplayer.com/blog/jellyfin-android-tv-clients-compared/)
- Kodi depends on libass (Arch package "required by" list includes mpv, Kodi, VLC's ASS plugin, and "Jellyfin's ffmpeg build"). — [Arch Linux libass package](https://www.archlinux.org/packages/extra/x86_64/libass)
- Forum users list Kodi among the working workarounds for ASS on Jellyfin. — [Jellyfin forum: will the Android TV app ever support ASS](https://forum.jellyfin.org/t-will-the-jellyfin-android-tv-app-ever-support-ass-subtitles?pid=44484)

**Swiftfin (iOS/tvOS) — libVLC (SwiftVLC); positional ASS rendered by VLC's ASS module; no explicit libass work**
- PR #2273 "VLCUI/VLCKit to SwiftVLC" merged 2026-09-05: SwiftVLC is "built on libvlc 4"; the maintainer says "positional image subtitles such as ASS/SSA are unaffected by the change"; text subtitle (SRT) styling planned for SwiftVLC 1.1.0; no plan to switch to mpv (maintainer wants VLC, mpv and AVPlayer all available "for a time"; mpv lacks immediate PiP). No libass or font-attachment handling is discussed. — [Swiftfin PR #2273](https://github.com/jellyfin/Swiftfin/pull/2273)
- Font selection bug: PR #2341 "Fix CJK subtitle rendering in VLC" found the VLC font option was applied only at playback start; the PR notes the maintainer "plans to drop VLC in favor of mpv, so it may not be merged" (conflicts with #2273's statement; both are the maintainer's words at different times). — [Swiftfin PR #2341](https://github.com/jellyfin/Swiftfin/pull/2341)
- Historical: early reports of ASS not displayed on iOS (issue #242) and external ASS/SRT not shown (#417). — [Swiftfin issue #242](https://github.com/jellyfin/Swiftfin/issues/242); [Swiftfin issue #417](https://github.com/jellyfin/Swiftfin/issues/417)
- CJK glyphs render as squares on iOS/tvOS in both Swiftfin (#2004) and Streamyfin (#1665), attributed to Apple removing a default Chinese font. — [Streamyfin issue #1665](https://github.com/streamyfin/streamyfin/issues/1665)

**Jellyfin Roku — cannot render ASS; burn-in**
- A Jellyfin core team member said the Roku app "cannot direct play ASS/SSA subtitles" and Roku allows no external player. — [Jellyfin forum: questions about Jellyfin for Roku](https://forum.jellyfin.org/t-questions-about-jellyfin-for-roku?pid=41642)
- Historical gap (May-Aug 2025): Roku lacked a "burn-in when transcoding" option; subtitles delivered separately desynced during transcodes; the "Force Transcoding" setting remuxed and omitted the `-filter-complex` burn-in argument the web client sends. — [jellyfin-roku issue #347](https://github.com/jellyfin/jellyfin-roku/issues/347)
- Fixed by jellyfin-roku PR #511 "Burn subtitles if transcoding. Force Transcode option updated to disallow remux", merged 2025-08-31; the Roku release containing it is not named on the PR. — [jellyfin-roku PR #511](https://github.com/jellyfin/jellyfin-roku/pull/511)
- The 2024-25 libass-wasm font-load failure also affected the Roku client (ASS not displaying when transcoding). — [jellyfin-web issue #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)

**Jellyfin for LG webOS / Samsung Tizen — depends on the TV's browser/native player; ASS inconsistent; burn-in when unsupported**
- Moderator: Jellyfin's webOS app "is dependent on the WebOS browser player's capabilities"; a user reports "ASS subtitle support is inconsistent" and that ASS was triggering transcoding on webOS. — [Jellyfin forum thread tid=5349](https://forum.jellyfin.org/printthread.php?tid=5349)
- A non-maintainer forum poster says the LG built-in player used by the webOS client "can only handle a few subtitle formats, notably .srt, .ass, and .ssa" and that otherwise "the server either transcodes and burns them in if it can, or the video won't play". — [Jellyfin forum thread tid=11765](https://forum.jellyfin.org/printthread.php?tid=11765)
- webOS GitHub issue exists about ASS on an LG OLED55CX. — [jellyfin-webos issue #143](https://github.com/jellyfin/jellyfin-webos/issues/143)
- A moderator noted SRT renders directly on nearly all devices "while ASS subs can still require burn-in." — [Jellyfin forum: HDR with subs](https://forum.jellyfin.org/t-hdr-with-subs?pid=42536)

### Inferences
- Summary matrix (inferred from the findings above):
  - Native libass, full typesetting incl. embedded fonts: Jellyfin Desktop/JMP (mpv), Jellyfin for Kodi, JellyCon, Streamyfin, Findroid (mpv mode), Wholphin (mpv mode), JellyPlay (mpv mode), Moonfin, MPV Shim, Infuse (with the Aug-2026 external-font regression).
  - Native libass but WebAssembly, browser-dependent, font loading via server: Jellyfin Web (and therefore the webOS/Tizen apps only insofar as they embed the web client, but their TVs' native players are what usually decide).
  - Experimental native libass (opt-in developer setting, beta only): Jellyfin Android TV 0.20.0-beta.x.
  - Burn-in or degrade: Jellyfin Android mobile (ExoPlayer; "ASS compatibility" strips styling, else server transcodes), Jellyfin Android TV 0.19.x stable (forces transcode), Roku (burn-in since PR #511), webOS/Tizen (TV player dependent, typically burn-in).
  - VLC-engine rendering (not libass proper, but VLC's ASS module is libass-based upstream): Swiftfin via SwiftVLC/libvlc 4; font-attachment fidelity not documented by Swiftfin.
- The Swiftly 2026 article's claim that the official Android TV app "adds Jellyfin's Media3 FFmpeg decoder and libass" conflates two things: the `org.jellyfin.media3:media3-ffmpeg-decoder` dependency (audio decoding) and the `io.github.peerless2012:ass-media` dependency (libass). The libass path is only in 0.20 betas and is off by default.

### Gaps
- I could not retrieve the exact label strings of jellyfin-web's "Burn subtitles" setting (e.g., "Only image formats" / "All complex formats" / "Always") from source; the DeepWiki page returned HTTP 429 twice. Forum citations confirm "all complex formats" exists.
- No source found documenting how Swiftfin/SwiftVLC handles MKV font attachments for ASS; Swiftfin's issue tracker had no ASS-font-specific issue.
- No jellyfin-tizen-specific ASS issue or doc was found; Tizen behavior is inferred from the shared web-client architecture and forum remarks only.
- Which Roku app release shipped PR #511 is not stated on the PR.

## Key Question 2: What did Jellyfin Android TV ship regarding libass? Which version, is it default, known issues?

### Takeaway
Jellyfin Android TV went through three phases: an experimental libass direct-play path existed in 0.19.0 betas but the preference was stripped from non-development builds and the library removed before 0.19.0 stable (Sept-Oct 2025); PR #5121 ("Support Advanced SubStation Alpha direct play", branch `libass`, using peerless2012's libass-android/ass-media Media3 extension) was merged 2026-03-05 and shipped in v0.20.0-beta.1 (2026-09-08) as an experimental, disabled-by-default developer-settings toggle; as of 2026-10-13 no 0.20.0 stable exists, so the stable app (v0.19.10, 2026-08-16) still forces server transcoding for ASS. Known problems are performance/refresh-rate on complex typesetting and a Media3-side attachment (font) bug.

### Cited Findings
- Historical baseline (2023): issue #2875 — the TV app "cannot display the SSA and ASS formats properly, so it forces transcoding for those files" and lacked the mobile app's "Allow SSA/ASS subtitles in direct play" toggle; closed wontfix 2023-07-08; maintainer hoped to add "proper support for it eventually". — [jellyfin-androidtv issue #2875](https://github.com/jellyfin/jellyfin-androidtv/issues/2875)
- Historical (Nov 2024): forum answer that no Android-compatible libass build existed, "which means exoplayer/media3 doesn't support rendering .ass currently"; v0.18.0 had just added PGS support. — [Jellyfin forum: will the Android TV app ever support ASS](https://forum.jellyfin.org/t-will-the-jellyfin-android-tv-app-ever-support-ass-subtitles); [Jellyfin blog: Android TV 0.18](https://jellyfin.org/posts/androidtv-v0.18.0/)
- 0.19.0 cycle (Sept 2025): the v0.19.0 release notes list "Add experimental ASS direct play using libass #4630", then "Remove libass preference in non-development builds #4876" and "Remove libass library #5032". — [v0.19.0 release](https://github.com/jellyfin/jellyfin-androidtv/releases/tag/v0.19.0)
- Issue #4922 "[v0.19.0-beta.1] ASS subtitle codec is not supported" (opened 2025-09-09, server 10.10.7): maintainer nielsvanvelzen stated SSA/ASS "are not supported in 0.19", pointed to PR #4876 removing the libass preference from non-development builds; closed not planned 2025-09-10. — [jellyfin-androidtv issue #4922](https://github.com/jellyfin/jellyfin-androidtv/issues/4922)
- 2025-11-25 maintainer comment on #2875: media3's SSA/ASS support is "near non-existent"; libass rendering was "held back from 0.19 because of performance problems"; he did not expect it in 0.20 and pointed to development-build PR #5121 for testing. 2025-11-27: "testing wasn't needed because he already knew performance was poor"; asked for someone with Android NDK/C experience to fix libass performance. — [jellyfin-androidtv issue #2875](https://github.com/jellyfin/jellyfin-androidtv/issues/2875)
- PR #5121 "Support Advanced SubStation Alpha direct play" by nielsvanvelzen: first activity 2025-11-09, marked ready 2026-03-05, merged into master 2026-03-05 (commit aa96464), branch `libass`, milestone v0.20.0, labels enhancement/playback/release-highlight. Description: "This implementation is still experimental and thus disabled by default", toggle in the app's developer settings. Linked: #2875 (closed), Wholphin#22 (open), libass-android#57 (closed), #5397 (closed). — [jellyfin-androidtv PR #5121](https://github.com/jellyfin/jellyfin-androidtv/pull/5121)
- Competing PR #5397 "Integrated libass-android to enable advanced subtitle rendering" by j3553a (opened 2026-02-07, closed unmerged 2026-04-03 as superseded: "the libass integration is now merged"). Details from its discussion: it integrated libass-android into the ExoPlayer backend with a developer toggle plus configurable glyph/cache sizes; claimed to fix issue #4728 (karaoke-styled subtitles slowing and freezing playback); on an Nvidia Shield raising the glyph cache from 1,024 to 10,000 with 128 MB cache "noticeably improved stability"; Niels said stability improved after the project "switched to the OpenGL overlay" and preferred fixing defaults upstream; peerless2012 updated defaults in libass-android v0.4.0; a 4K suggestion was 256 MB cache. — [jellyfin-androidtv PR #5397](https://github.com/jellyfin/jellyfin-androidtv/pull/5397)
- The library: peerless2012/libass-android provides `lib_ass` (native libass.so), `lib_ass_kt` (Kotlin wrapper) and `lib_ass_media` (a Media3 extension); MIT licensed; "Who is using" lists Jellyfin Android TV, AfuseKt, Fladder, NuvioTV. — [peerless2012/libass-android](https://github.com/peerless2012/libass-android)
- libass-android issue #57 "ASS renderer refresh rate seems too low" (opened 2025-11-07 by a Jellyfin Android TV user on Shield Pro 2019): moving signs "jump from a position to another one", late appear/clear. Latest stable remains v0.19.10 (16 Aug 2026); v0.19.4-v0.19.9 (Nov 2025-May 2026) have no ASS-related lines. — [jellyfin-androidtv releases](https://github.com/jellyfin/jellyfin-androidtv/releases); [v0.20.0-beta.3](https://github.com/jellyfin/jellyfin-androidtv/releases/tag/v0.20.0-beta.3)

- Historical: certain media with embedded ASS failed to play in ExoPlayer; LibVLC played it but never displayed the subs; closed not planned. — [jellyfin-androidtv issue #3373](https://github.com/jellyfin/jellyfin-androidtv/issues/3373)

### Inferences
- Through 2026-10-13 no production (Play Store stable) Jellyfin Android TV build renders ASS natively. Users must sideload/join the 0.20 beta, enable developer settings, and toggle the experimental libass option. Everyone else gets server burn-in.
- The implementation is libass via OpenGL overlay (per the PR #5397 discussion and libass-android #57), with frame-timing limitations inherited from Media3; smooth \move/karaoke on 4K output is the known weak spot.
- "Add option to always burn in subtitles when transcoding" (#4459) in the same beta gives TV users a way to avoid the desync of separately delivered subs, but it is a burn-in control, not native rendering.

### Gaps
- PR #5121's page does not describe font/attachment handling (whether MKV font attachments are fetched from the server's attachments API and passed to libass). The attachment issue referenced in libass-android #57 (androidx/media#2536) was not fetched.
- The 0.20.0 stable release date is unknown; betas ran Sept 2026.
- Issue #4728 (karaoke freezes) was not fetched directly; its content is known only via PR #5397.

## Key Question 3: What does Jellyfin server do with embedded fonts (MKV attachments) during burn-in, and what are the common failure modes?

### Takeaway
During burn-in jellyfin-ffmpeg's libass reads fonts from a per-media `fontsdir` populated by the server's AttachmentExtractor (MKV font attachments extracted to the cache's attachments folder) plus system fonts and an admin-configured fallback-font folder; the documented failure modes are the extractor not running on some client paths (default font substituted), external .ass files that cannot use fonts attached inside the MKV, missing CJK/Arabic system fonts (boxes), and (fixed in 12.0) SSA-to-ASS conversion that overwrote styles with a hardcoded Arial.

### Cited Findings
- Attachment extraction path: jellyfin issue #13914 (server 10.10.7, jellyfin-ffmpeg 7.0.2) shows the web playback path runs AttachmentExtractor before transcoding, filling `/cache/attachments/`, and the ffmpeg command references a fontsdir; on the Android client path that step was skipped so the folder stayed empty and burned-in ASS "fell back to a default font". Playing once in a browser first made fonts work. Maintainers moved it to "Wrong Repo"/"Insufficient Data", never confirmed the diagnosis; closed by bot as not planned 2025-09-05. — [jellyfin issue #13914](https://github.com/jellyfin/jellyfin/issues/13914)
- System fonts required: In the Android TV external-fonts thread the maintainer said "the server needs font access to bake subtitles in"; the reporter found the docs say fonts must be installed system-wide and "Mounting a fonts folder into their containerized server made ExoPlayer render the fonts correctly" (closed not planned 2024-08-11). — [jellyfin-androidtv issue #3854](https://github.com/jellyfin/jellyfin-androidtv/issues/3854)
- External ASS + embedded MKV fonts: with "burn in all complex formats" the server "pulled fonts from the video file" so embedded subtitle tracks rendered Arabic correctly while external subtitles rendered boxes (Mar 2024, historical). — [Jellyfin forum: subtitle does not display correctly](https://forum.jellyfin.org/t-subtitle-does-not-display-correctly)
- Fallback fonts: Jellyfin has a transcoding setting "Enable fallback fonts" with a fallback-font path; a user placing a Google font converted to woff2 in that folder still saw missing subtitles (unresolved thread). — [Jellyfin forum thread tid=14351](https://forum.jellyfin.org/printthread.php?tid=14351). In the libass-wasm bug, users put e.g. Roboto-Regular.ttf in the server's fonts directory; a member warned fallback fonts "too large for the browser (over 20MB)" could break web rendering. — [jellyfin-web issue #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)
- Historical 10.10.0/10.10.1 regression (Nov 2024-Feb 2025): "libass: Failed to load fonctconfig fonts!" on files with no font attachments broke ASS on web, Android and Roku; resolved by clearing the subtitle cache (config data dir) and by the FFmpeg bundled with 10.10.5; closed 2025-01-26. — [jellyfin-web issue #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)
- SSA style loss (not font files, style replacement): issue #14708 (10.10.7, FFmpeg 7.1.1): when an external .ssa is served as .ass, Jellyfin replaced the style block with a single hardcoded "Arial" size-20 style (`AssWriter.cs`); burn-in rendered correctly but non-burn-in delivery lost styles; root cause: Jellyfin treated .ssa as .ass; nyanmisaka proposed skipping conversion since libass detects format from content; closed completed 2026-05-03 by PR #16744. — [jellyfin issue #14708](https://github.com/jellyfin/jellyfin/issues/14708); [jellyfin PR #16744 "Avoid SSA to ASS conversion and loss of styles"](https://github.com/jellyfin/jellyfin/pull/16744)
- Jellyfin 12.0 release post: "Subtitle writing now uses SubtitleEdit, which avoids the old SSA to ASS conversion" and its styling loss. — [Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/)
- Jellyfin does not ship fonts: in #14708 nyanmisaka "replied that Jellyfin does not supply fonts". — [jellyfin issue #14708](https://github.com/jellyfin/jellyfin/issues/14708). Earlier: "Jellyfin doesn't provide any CJK fonts by default". — [jellyfin-web issue #1670](https://github.com/jellyfin/jellyfin-web/issues/1670)
- CJK boxes with burn-in on Android TV; suggested server fix `fonts-noto-cjk-extra` (user suggestion, Sept 2026). — [jellyfin-androidtv issue #5507](https://github.com/jellyfin/jellyfin-androidtv/issues/5507)
- Burn-in ignores client subtitle appearance settings: "client-side font size and color settings don't affect burned-in subtitles, because the server renders them with FFmpeg". — [Jellyfin forum: changing font size for transcoded subtitles](https://forum.jellyfin.org/t-changing-font-size-for-transcoded-subtitles)
- Slow burn-in start when ASS lacks sizes: ffmpeg probes the whole file; workaround was extracting subs to the config folder and raising analyzeduration/probesize (2024, historical). — [Jellyfin forum: subtitle burn in won't use extracted embedded subtitles](https://forum.jellyfin.org/t-subtitle-burn-in-won-t-use-extracted-embeded-subtitles)
- Burn-in with hardware transcoding: docs list "Video Subtitle burn-in (optional)" as a pipeline stage and warn "Some of these stages cannot be GPU accelerated due to software, hardware or driver limitations", with partial acceleration meaning higher CPU use. — [Jellyfin docs: Hardware Acceleration](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/). 10.11.0: "We now have more accurate rendering of ASS/SSA subtitles when using hardware transcoding." — [Jellyfin 10.11.0 release post](https://jellyfin.org/posts/jellyfin-release-10.11.0/)
- Historical Roku symptom: movies stopped playing when ASS enabled; moderator guessed the server was burning in and hardware acceleration was suspected. — [Jellyfin forum thread tid=12531](https://forum.jellyfin.org/printthread.php?tid=12531)
- Feature request remains open for a GUI option to let users specify SSA/ASS fonts. — [Jellyfin feature request #743](https://features.jellyfin.org/posts/743/add-an-gui-option-to-allow-user-specify-ssa-ass-subtitle-fonts)

### Inferences
- The practical burn-in fidelity rule: embedded ASS track + fonts attached in the same MKV = typesetting generally preserved (fonts extracted to attachments cache); external .ass sidecar = only system/fallback fonts available, so signs render in substitute fonts and mis-size/mis-position; CJK/Arabic scripts need server-installed fonts (e.g., Noto CJK) or they render as boxes.
- Burn-in correctness is path-dependent: #13914 shows a client that requests transcode without triggering attachment extraction yields wrong fonts on first play; this is an unconfirmed diagnosis but matches the "play in browser first" workaround.

### Gaps
- No official doc page describing AttachmentExtractor, the attachments cache path, or the exact ffmpeg `fontsdir`/`-filter_complex subtitles=...:fontsdir=` command construction was retrieved; evidence is from issue logs.
- Whether 12.0's "prune extracted subtitles and attachments on scan" (introduced 10.11.0) interacts with the cold-cache font problem is not documented.
- No source quantifies how often hardware-accelerated burn-in (overlay_qsv/overlay_vaapi etc.) mis-positions signs; the 10.11.0 note implies prior inaccuracy but gives no detail.

## Key Question 4: Which Jellyfin server versions (10.9, 10.10, 10.11, 12.x) changed anything about subtitle handling?

### Takeaway
10.9 (May 2024) added dual simultaneous subtitle tracks in web; 10.10 (Oct 2024) added client-side PGS rendering in web and had a libass font-loading regression fixed in 10.10.5; 10.11 (Oct 2025) added more accurate ASS/SSA rendering under hardware transcoding, a toggle to disable native subtitle styling, and pruning of extracted subtitles/attachments on scan; 12.0 (Sept 2026, FFmpeg 8.1) moved subtitle writing to SubtitleEdit (no more SSA-to-ASS style loss), made subtitle settings per-library, added configurable extraction timeout, embedding external subs into MKV output, VobSub via libbitsub, and race-condition fixes.

### Cited Findings
- 10.9.0 (2024-05-11): "We now support multiple simultaneous subtitle tracks (maximum of two, a primary and secondary) in the web player"; "Support for hearing-impaired subtitles (sdh/hi./cc)". Nothing on ASS/burn-in. — [Jellyfin 10.9.0 release post](https://jellyfin.org/posts/jellyfin-release-10.9.0/)
- 10.10.0 (2024-10-26): Web gained "client-side rendering of PGS subtitles"; no ASS-specific lines. — [Jellyfin 10.10.0 release post](https://jellyfin.org/posts/jellyfin-release-10.10.0/)
- 10.10.0/10.10.1 regression: ASS/SSA stopped rendering on transcode (libass "Failed to load fontconfig fonts"); fixed FFmpeg shipped in 10.10.5 (Feb 2025); clearing the subtitle cache was the workaround. — [jellyfin-web issue #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)
- 10.11.0 (2025-10-19): "Native styling of subtitles can be disabled"; "We now have more accurate rendering of ASS/SSA subtitles when using hardware transcoding"; on file replacement Jellyfin will "prune related data (chapters, trickplay files and extracted subtitles and attachments) on scan". — [Jellyfin 10.11.0 release post](https://jellyfin.org/posts/jellyfin-release-10.11.0/)
- 10.11.x point releases (per third-party aggregators): subtitle writing through SubtitleEdit avoiding SSA-to-ASS style loss, configurable extraction timeout, fixes for concurrent-conversion races and ffmpeg hangs during extraction. (Aggregator; verify.) — [releasebot.io Jellyfin](https://releasebot.io/updates/jellyfin); [VideoHelp version history](https://www.videohelp.com/software/Jellyfin/version-history)
- 12.0 (2026-09-07): versioning drops the "10." prefix ("What would have been 10.12.0 is simply 12.0"); "the new upstream FFmpeg 8.1"; "Subtitle settings are now configured per library"; subtitle writing uses SubtitleEdit, avoiding "the old SSA to ASS conversion"; VobSub support added; "External subtitles can be embedded into MKV when transcoting"; configurable subtitle extraction timeout; clients can render image-based subtitles during remuxing. — [Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/)
- 12.0 detail from secondary coverage: "VobSub subtitle rendering via libbitsub (replacing libpgs)"; "Fixed race conditions in concurrent subtitle conversion". — [JellyWatch: Jellyfin 12 release](https://jellywatch.app/blog/jellyfin-12-release-everything-you-need-to-know); [NAS Compares: 12.0 RC1](https://nascompares.com/news/jellyfin-12-0-rc1-released-faster-performance-better-playback-and-major-library-fixes/)
- PR #16744 (merged 2026-05-03) sits on the "Jellyfin v12" project board; no 10.11.x backport noted. — [jellyfin PR #16744](https://github.com/jellyfin/jellyfin/pull/16744)
- Official Subtitle Extract plugin added "Jellyfin 10.11 support"; a core team member said the plugin "doesn't change transcoding requirements". — [jellyfin-plugin-subtitleextract releases](https://github.com/jellyfin/jellyfin-plugin-subtitleextract/releases); [Jellyfin forum: extracted subtitles](https://forum.jellyfin.org/t-how-to-use-extracted-subtitles-from-subtitle-extract-plugin?pid=13793)

### Inferences
- Nothing in 10.9-12.0 changes the fundamental model: the server never sends fonts to a client that cannot render ASS; it either hands the ASS to a capable client (plus attachment/font endpoints) or burns in. The meaningful server-side ASS improvements are correctness fixes (HW-transcode accuracy in 10.11, SSA style preservation in 12.0) rather than new capabilities.

### Gaps
- The exact 10.11.x point release numbers for the SubtitleEdit/extraction-timeout changes come only from aggregators; official per-point-release notes were not fetched.
- The official 10.11.0 and 12.0 posts do not mention fonts or burn-in explicitly; the HW-transcode ASS accuracy PR was not identified.

## Key Question 6: What are the recommended community workarounds for anime?

### Takeaway
Community advice converges on: use an mpv-based client (Jellyfin Desktop/JMP, MPV Shim, Streamyfin, Findroid, Wholphin) or Kodi for native typesetting; on Android TV/mobile either use an external player (mpv-android, VLC, MX Player) or opt into the 0.20 beta's experimental libass; otherwise force server burn-in ("burn in all complex formats"/"always burn in when transcoding"), install the needed fonts (e.g., Noto CJK) on the server, and mux fonts and ASS into the MKV rather than using sidecar files.

### Cited Findings
- Client choice: a 2026 guide says ASS can look wrong when it references fonts the client lacks and recommends SRT or "a client with ASS support such as Jellyfin Media Player or mpv-based clients". — [JellyWatch: Jellyfin Subtitles Guide 2026](https://jellywatch.app/blog/jellyfin-subtitles-complete-guide-2026)
- Forum: JMP and MPV Shim handle ASS best; on Android install MPV/VLC/MX Player and set Jellyfin to open videos in them. — [Jellyfin forum: ASS subtitles not supported](https://forum.jellyfin.org/t-ass-subtitles-not-supported?pid=18157)
- Android TV: install MPV or VLC and set "external player", or force transcoding to burn in; note the VLC trick "only works for the newer Android TV and not on the ChromeCast". — [Jellyfin forum: ASS fonts issue](https://forum.jellyfin.org/t-ass-fonts-issue); [Jellyfin forum thread tid=9950](https://forum.jellyfin.org/printthread.php?tid=9950)
- Burn-in: choose "burn in all complex formats" per client (web). — [Jellyfin forum](https://forum.jellyfin.org/t-subtitle-does-not-display-correctly). Android TV 0.20 beta adds "Add option to always burn in subtitles when transcoding". — [v0.20.0-beta.1](https://github.com/jellyfin/jellyfin-androidtv/releases/tag/v0.20.0-beta.1). Roku burns in when transcoding since PR #511. — [jellyfin-roku PR #511](https://github.com/jellyfin/jellyfin-roku/pull/511)
- Fonts on server: mount a fonts folder into the container / install system-wide so ffmpeg can bake them. — [jellyfin-androidtv #3854](https://github.com/jellyfin/jellyfin-androidtv/issues/3854). Install `fonts-noto-cjk-extra` for CJK. — [jellyfin-androidtv #5507](https://github.com/jellyfin/jellyfin-androidtv/issues/5507). Use the "Enable fallback fonts" transcoding setting with a fonts folder (mixed results). — [forum tid=14351](https://forum.jellyfin.org/printthread.php?tid=14351)
- Clear the subtitle cache after upgrades if ASS stops rendering (historical 10.10 fix). — [jellyfin-web #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)
- Mux rather than sidecar: Infuse external-font bug fixed by muxing .ass into the MKV; Jellyfin burn-in pulls fonts only from the video file. — [Firecore](https://community.firecore.com/t/bug-external-ass-subtitles-ignoring-embedded-mkv-fonts-in-infuse-8-5/60462); [Jellyfin forum](https://forum.jellyfin.org/t-subtitle-does-not-display-correctly)
- Kodi as frontend: listed by forum users as a working alternative; Jellyfin for Kodi v2.2.0 / JellyCon v1.0.2 use Kodi's own (libass) player. — [forum](https://forum.jellyfin.org/t-will-the-jellyfin-android-tv-app-ever-support-ass-subtitles?pid=44484); [Swiftly comparison](https://swiftlyplayer.com/blog/jellyfin-android-tv-clients-compared/)
- Third-party Android TV: Wholphin routes SSA/ASS files to its MPV backend automatically; Findroid's mpv mode. — [Swiftly comparison](https://swiftlyplayer.com/blog/jellyfin-android-tv-clients-compared/); [F-Droid Findroid](https://f-droid.org/de/packages/dev.jdtech.jellyfin/)
- Tooling: "fontInAss" is a community tool that embeds fonts into ASS files for players that lack font access (listed in search results; not evaluated). — [fontInAss](https://tomevault.io/tome/RiderLty/fontInAss)

### Inferences
- For a pure-anime library on October 2026 Jellyfin, the lowest-friction fully correct stack is: fonts + ASS muxed into MKV, served to Jellyfin Desktop (mpv) / Kodi / Streamyfin / Findroid / Wholphin. For the official Android TV app, wait for 0.20.0 stable and enable the experimental libass toggle, or keep burn-in and install fonts server-side.

### Gaps
- No Jellyfin-official documentation page exists (that I found) describing recommended anime/ASS setups; all workaround guidance is forum/community.
- r/jellyfin and r/animepiracy wiki pages were not directly retrieved (search did not surface them); their guidance is likely consistent with the forum material but is uncited here.
