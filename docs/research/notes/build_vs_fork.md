# Build vs. fork vs. new client: a libass-first "Jellyfin replacement" in 2026

Research date: 2026-10-13. Activity data (pushed_at, stars, release dates) comes from the GitHub REST API on that date unless stated otherwise. "Pushed" = last push to any branch, which overstates health for repos that only receive dependency bumps.

## Key question 1: What exact Jellyfin/Emby endpoints do Sonarr/Radarr call, and can a new server implement a compatible subset so they "just work"?

### Takeaway
The surface is small and well-defined: Sonarr's Emby/Jellyfin "Connect" uses only four endpoints. A new server that implements this subset with Jellyfin's `Authorization: MediaBrowser ...` header scheme and Jellyfin's item JSON shape for series lookups (Path, ProviderIds) would be a drop-in for Sonarr/Radarr's library-update notification.

### Cited Findings
- Sonarr's Emby/Jellyfin notification proxy (`MediaBrowserProxy.cs`) uses only: `GET /System/Configuration` (test connection), `POST /Notifications/Admin` (JSON `Name`, `Description`, `ImageUrl`), `GET /Items?recursive=true&includeItemTypes=Series&fields=Path,ProviderIds&years=` (to find the series path by TVDB/IMDb/TVMaze/TMDb/TVRage ID or title), and `POST /Library/Media/Updated` (JSON `Updates: [{Path, UpdateType}]`). It sends both `X-MediaBrowser-Token: <ApiKey>` and `Authorization: MediaBrowser Token="<ApiKey>"` on every request and does not distinguish Emby from Jellyfin — [Sonarr MediaBrowserProxy.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/MediaBrowser/MediaBrowserProxy.cs)
- Third-party docs describe Jellyfin's auth header as the `MediaBrowser` scheme with comma-separated quoted values (Client, Version, DeviceId, Device, Token), e.g. `Authorization: MediaBrowser Token="..."`, with `X-Emby-Authorization`/`X-MediaBrowser-Token` as legacy headers that newer servers may reject and `ApiKey` query param as a last resort — [mintlify mirror of Jellyfin auth docs](https://www.mintlify.com/jellyfin/jellyfin/api/authentication/overview)
- Jellyfin 12.0 removed support for the legacy `/emby/` and `/mediabrowser/` address prefixes and disabled the deprecated sign-in method, including on existing servers; the post warns clients not updated in years are at risk — [Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/)
- Autoscan is an alternative pattern: Sonarr/Radarr Connect webhooks go to Autoscan, which then triggers Plex/Jellyfin/Emby library scans using an API key — [ultra.cc Autoscan guide](https://docs.ultra.cc/books/unofficial-application-installers/page/autoscan/revisions/3335)

### Inferences
- Because Sonarr sends `X-MediaBrowser-Token` as well as the `Authorization` header, a new server should accept both; Jellyfin 12's deprecation of legacy headers means that is already a moving target for Jellyfin itself, so a new server should accept the modern header first.
- Sonarr's `/Library/Media/Updated` is path-based: the new server must expose library item `Path` values that match what Sonarr sees on its own filesystem (same mount paths or path mappings), exactly as Jellyfin does today.

### Gaps
- I did not fetch Radarr's equivalent proxy; it is the same NzbDrone.Core code lineage as Sonarr and is very likely identical, but this was not verified.
- I did not pull the Jellyfin OpenAPI spec (api.jellyfin.org) to confirm exact response schemas; the field list above is what Sonarr actually reads, which is the practical minimum.

## Key question 2: Plex-API-compatible approaches

### Takeaway
No open-source server that reimplements the Plex Media Server protocol for official Plex clients was found. Emulating a small Plex surface for arr purposes may be feasible, but the Jellyfin API is the better target because it is open, documented, and already supported by the whole third-party client ecosystem.

### Cited Findings
- A search for an open-source Plex Media Server reimplementation returned only client libraries (python-plexapi, the Rust `plex-api` crate described as "not ready for any use", .NET Plex.Api) and tools like plex-dvr-hls that emulate an HDHomeRun tuner, not the server — [search summary: lib.rs plex-api](https://lib.rs/crates/plex-api); [PlexAPI on PyPI](https://pypi.org/project/PlexAPI/2.0.1/)
- Dim (Rust) was described in 2022 as a media manager that "emulates Plex's appearance and functionality as closely as possible", i.e. a UI clone, not a protocol-compatible server — [Linux Magazine on Dim](https://www.linux-magazine.com/Issues/2022/260/Dim-Media-Manager)

### Inferences
- Plex emulation would only buy arr compatibility (same as the Jellyfin route) and could not legally or practically bring official Plex clients along, since those authenticate via plex.tv. The Jellyfin API is the only open target that also unlocks existing third-party clients (Streamyfin, Findroid, Wholphin, Swiftfin, Tsukimi, Jellyfin-Vue).

### Gaps
- The Plex endpoints that Sonarr/Radarr's Plex Connect calls were not fetched, so the exact Plex surface the arr apps need is unverified.

## Key question 3: Existing open-source servers/clients (Rust/Go/TS) with 2025–2026 activity, and is there already a "Jellyfin-API-compatible server with mpv clients"?

### Takeaway
No project implements a Jellyfin-compatible API on a new server with mpv-based clients. The closest things are: (a) Kyoo, an actively developed TS/Go/Python server with its own API, libass-correct subtitle handling, OIDC, and an Android TV client merged into master in Sept–Oct 2026 but not yet released; and (b) a thriving ecosystem of third-party Jellyfin clients that embed libmpv (Streamyfin, Findroid, Wholphin, Tsukimi, Seanime's desktop player). Dim, Olaris and Zenith are effectively dead; Reiverr is a Jellyfin-backed front-end, not a server.

### Inferences
- Activity ranking (healthy → dead): Kyoo, Seanime, Shoko/Shokofin, Streamyfin, Findroid, Wholphin, Tsukimi, Reiverr all pushed within the last week. Dim (last push Sept 2025, 161 open issues) and Olaris are dead for practical purposes; Zenith is a personal project with no community. Forking Dim or Olaris would mean inheriting a stale Rust/Go codebase with no maintainers.
- Kyoo is the only candidate for "fork an existing new-generation server": it already has libass-correct subtitle handling with embedded fonts, OIDC, HLS transcoding with hwaccel, and an in-progress Android TV client. Its cost is a bus factor of one, a v5 rewrite that temporarily dropped features, and a custom API (so arr compatibility would have to be added as a Jellyfin-shim layer).
- Shoko is complementary rather than competitive: its value is AniDB-driven metadata for anime, and Shokofin shows it is designed to plug into a media server rather than be one.
- The "mpv-based Jellyfin clients" half of the question is already solved in several codebases (Wholphin for Android TV with ExoPlayer+libass and mpv, Streamyfin with its own mpv-player native module for mobile and TV, Findroid with mpv for phones). This is strong evidence that option (c), building or adopting a client layer on the Jellyfin API, has the most reusable prior art.

## Key question 4: Which Android TV rendering stack is most practical for libass with hardware decode, and what is known about performance on Shield / Google TV Streamer / Fire TV?

### Takeaway
Two viable stacks exist in 2026: (1) Media3/ExoPlayer plus the `io.github.peerless2012:ass-media` libass extension (used by the official Jellyfin Android TV app on master, Wholphin, Fladder, NuvioTV), which keeps the platform decoder path and adds a libass overlay; and (2) embedded libmpv with `hwdec=mediacodec` (mpv-android's MPVLib as reference, libmpv-android, media_kit for Flutter, Streamyfin's native module). The official Jellyfin TV app's libass integration has been unstable (added April 2025, removed from the 0.19 release in Oct 2025 as "can't be turned on", re-bumped to ass-media 0.5.1 in Aug 2026). No device-specific benchmark for mpv+mediacodec+libass on Shield or Google TV Streamer was found.

### Cited Findings
- libass-android (peerless2012) ships three modules: `lib_ass` (native libass.so with prefab), `lib_ass_kt` (Kotlin wrapper), and `lib_ass_media` ("a media3 extension" letting Media3-based players render libass subtitles); MIT; "Who is using" lists Jellyfin Android TV, Fladder and NuvioTV; 89 stars, 201 commits — [libass-android](https://github.com/peerless2012/libass-android)
- Latest libass-android release is v0.5.1 (2026-08-11), a fix to stop the view calling invalidate after detach — [GitHub API releases](https://api.github.com/repos/peerless2012/libass-android/releases/latest)
- Maven artifact `io.github.peerless2012:ass-media` is described as "Androidx media extension for libass" — [Sonatype Central](https://central.sonatype.com/artifact/io.github.peerless2012/ass-media)

- A Plex forum user reports "On the Nvidia Shield the MPV backend doesn't really work, it has an issue with stuttering. ### Inferences
- Media3 + ass-media is the lower-risk path for an Android TV client because it keeps Google's MediaCodec/tunneled playback, Leanback/Compose-for-TV focus handling, DRM-free HDR passthrough handling, and the existing Jellyfin SDK; the libass overlay is the only native component. Its risk is that the extension is one person's project (peerless2012) and the official Jellyfin app had to pull it from a release once.
- Embedded libmpv gives the best ASS fidelity and codec breadth (mpv's `sd_ass` path makes libass mandatory for all text subs) but you own the whole pipeline: hwdec quirks per SoC, HDR/Dolby Vision handling, audio passthrough, and a 20–40 MB native payload. Wholphin's "two engines" design (ExoPlayer default, MPV for hard files) is the pragmatic hedge both Findroid and Wholphin landed on independently.
- Flutter/media_kit and React Native (Streamyfin's in-repo mpv module) are viable only if the team already prefers those frameworks; neither offers TV-specific focus/remote handling out of the box, and media_kit's 359 open issues plus Aug 2026 last push suggest slower maintenance than the Kotlin options.
- Device performance: the only hard datum is that Shield decodes 4K HEVC in hardware; everything else about mpv+mediacodec on Shield/Google TV Streamer/Fire TV is anecdotal and mixed. Plan on a test matrix and a per-device fallback (burn-in or ExoPlayer) rather than assuming libass overlays are free on low-end Fire TV sticks.

### Gaps
- No measured benchmark (frame drops, CPU use) of mpv-android or ass-media rendering heavy typesetting ASS on Shield, Google TV Streamer, or Fire TV 4K was found.
- Whether the official Jellyfin Android TV app will ship libass enabled in 0.20 is unknown; master contains the dependency but the last shipped release does not advertise it.
- Kotlin Multiplatform / Compose for TV with libass was not investigated; no sources surfaced.

## Key question 5: Other platforms — Apple TV, web (jassub vs. SubtitlesOctopus, what jellyfin-web uses), Roku/webOS/Tizen

### Takeaway
Web: jellyfin-web (v13.0.0) renders ASS with `@jellyfin/libass-wasm` 4.2.4, Jellyfin's own fork of JavascriptSubtitlesOctopus; it tried JASSUB in 2023 and migrated back in March 2024 for legacy-browser compatibility. Upstream libass/JavascriptSubtitlesOctopus has been dormant since Sept 2024 while jassub (ThaUnknown) is actively maintained (pushed Oct 2026), so a new web client would pick jassub unless it must support old smart-TV browsers. Apple TV: MPVKit builds libmpv for tvOS but its own README says it is for learning and not frequently maintained; Swiftfin's tvOS subtitle story is still a sore point in forums. Roku cannot render ASS at all and must burn-in; webOS/Tizen are unverified but forum reports say unsupported formats force burn-in.

### Cited Findings

### Inferences
- For a new web client, jassub is the right choice in 2026 (active, TypeScript, async rendering); Jellyfin's revert was driven by legacy browser support that a greenfield client can decline. If Tizen/webOS TV browsers are targets, test jassub's WASM/OffscreenCanvas requirements early since that is exactly where Jellyfin got burned.
- On Apple TV, the practical options are VLCKit (Swiftfin's historical choice) or a libmpv build; the MPVKit upstream disclaims production use, so a team would be maintaining its own libmpv/libass build scripts for tvOS. Treat Apple TV as a second-tier, higher-maintenance target.
- Roku, webOS and Tizen cannot be made libass-correct on-device; the server must support "burn-in via libass in ffmpeg" as a first-class transcode mode regardless of which option (build/fork/client) is chosen.

### Gaps
- Swiftfin's current (2026) player engine and whether it uses MPVKit or VLCKit on tvOS was not confirmed from Swiftfin's own source.
- No authoritative Tizen/webOS subtitle-format documentation was found.

## Key question 6: Server-side ffmpeg, metadata providers, and auth (local users, OIDC)

### Takeaway
jellyfin-ffmpeg is a drop-in dependency: GPL-licensed portable builds of FFmpeg 8.1.3 for Linux (amd64/arm64), macOS and Windows with Jellyfin's hwaccel/Vulkan patches, released Sept 2026. Metadata: TMDB/TVDB are the baseline IDs the arr apps key on in ProviderIds; AniDB is the anime key (mapped via anime-lists) and Shoko is the best-of-breed anime metadata sidecar. Auth: Jellyfin still has no native OIDC in 2026 (only community plugins that largely work in browser only), which is a real differentiator a new server or Kyoo already offers.

### Cited Findings
- jellyfin-ffmpeg latest release v8.1.3-1 (2026-09-27): "Upgrades to upstream FFmpeg version 8.1.3", fixes MSDK hwupload instability on Windows, backports Vulkan fixes; assets: .deb for Debian bookworm/trixie and Ubuntu jammy/noble/resolute (amd64, arm64), portable linux64/linuxarm64 `-gpl` tarballs, mac64/macarm64 tarballs, win64/winarm64 clang `-gpl` zips — [GitHub API releases](https://api.github.com/repos/jellyfin/jellyfin-ffmpeg/releases/latest)
- jellyfin-ffmpeg repo describes itself as "FFmpeg for Jellyfin with custom extensions and enhancements"; build scripts exist for linux-amd64, linux-arm64, windows-win64; multiple license files (GPL-2.0/3.0, LGPL-2.1/3.0) — [jellyfin-ffmpeg](https://github.com/jellyfin/jellyfin-ffmpeg)
- Jellyfin 12.0 ships FFmpeg 8.1 per third-party coverage — [JellyWatch Jellyfin 12 summary](https://jellywatch.app/blog/jellyfin-12-release-everything-you-need-to-know)
- Kyoo's gocoder: lazy HLS transcoding with vaapi/qsv/cuda hardware acceleration, usable outside Kyoo, JWT auth on the TODO list — [pkg.go.dev gocoder](https://beta.pkg.go.dev/github.com/zoriya/kyoo/transcoder)
- Shoko Server: anime metadata aggregator that integrates directly with media software; Shokofin plugin for Jellyfin is actively pushed (Oct 2026) — [ShokoServer API](https://api.github.com/repos/ShokoAnime/ShokoServer); [Shokofin API](https://api.github.com/repos/ShokoAnime/Shokofin)
- Seanime uses AniList exclusively and explicitly will not support MAL/Trakt/SIMKL — [Seanime README](https://raw.githubusercontent.com/5rahim/seanime/main/README.md)
- Jellyfin OIDC status: a Jellyfin GitHub discussion states Jellyfin "currently has no native external authentication support" with an RFC proposing server-level OIDC via a Quick Connect bridge first; the original 9p4 SSO plugin was archived; "Flowfin" is a security-focused revival targeting Jellyfin 10.11 (.NET 9) and 12.0 (.NET 10) in 4.3.0 beta; Pocket ID's guide warns the SSO plugin integration "will only work in a browser" with Quick Connect as the native-app workaround; JellyfinSecurity plugin v2.5.16–2.5.20 adds OIDC+MFA for 10.11.9+ — [Jellyfin discussion #16470](https://github.com/orgs/jellyfin/discussions/16470); [Flowfin 4.3.0-beta.9](https://newreleases.io/project/github/Flowfin/jellyfin-plugin-sso/release/4.3.0-beta.9); [Pocket ID Jellyfin guide](https://pocket-id.org/docs/client-examples/jellyfin); [JellyfinSecurity v2.5.20](https://newreleases.io/project/github/ZL154/JellyfinSecurity/release/v2.5.20)
- Kyoo: OIDC with any compliant provider; auth is a separate service (`kyoo_auth`) and the transcoder validates JWTs via a JWKS URL — [Kyoo README](https://raw.githubusercontent.com/zoriya/Kyoo/master/README.md); [selfhostedworld Kyoo compose](https://selfhostedworld.com/software/kyoo)
- Jellyfin 12.0 upgrade requires being on 10.10.7 or 10.11.x first, a full library scan afterwards, and fails migration when usernames differ only by case; plugins must be rebuilt for 12 — [Jellyfin 12.0 post](https://jellyfin.org/posts/jellyfin-release-12.0/)

### Inferences
- A new server should shell out to jellyfin-ffmpeg rather than vendor FFmpeg: it gets Jellyfin's tested hwaccel matrix (VAAPI/QSV/NVENC/Vulkan/AMF/VideoToolbox) and libass burn-in for free, with GPL licensing implications for anything that links it (shelling out avoids that).
- If Jellyfin-style arr integration matters, the server must store TMDB/TVDB/IMDB IDs under Jellyfin's `ProviderIds` key names (`Tmdb`, `Tvdb`, `Imdb`), whatever the internal provider is, because Sonarr's Connect finds series by those IDs.
- OIDC is the clearest functional gap in Jellyfin today and is where a fork or new server can differentiate; but note native clients also need an OIDC flow (device code or PKCE in a WebView), which is a client-side cost in option (c) too.

### Gaps
- The exact set of Jellyfin-specific patches in jellyfin-ffmpeg (tone mapping, subtitle filters) was not enumerated; the repo README is upstream's.
- No source on AniList-as-provider in a Jellyfin-compatible server.

## Key question 7: Scope comparison — new client (Android TV + web) on Jellyfin API vs. forking vs. new server; what have people who tried learned?

### Takeaway
Evidence from the field strongly favors building clients on the Jellyfin API: every active "alternative" project with real users is a client (Streamyfin, Findroid, Wholphin, Tsukimi, Jellyfin-Vue, Reiverr), while the full-server attempts are either dead (Dim, Olaris, Zenith) or single-maintainer with a years-long client backlog (Kyoo: Android TV requested Dec 2023, first PR merged Sept 2026). The libass problem is overwhelmingly a client problem; the server side only needs burn-in (already in jellyfin-ffmpeg) and correct font attachment serving (already in Jellyfin's API).

### Cited Findings
- Kyoo is "developed by one person" and invites contributions for more clients; its v5 rewrite temporarily removed watch-list sync and offline downloads — [Kyoo README](https://raw.githubusercontent.com/zoriya/Kyoo/master/README.md)
- Kyoo Android TV timeline: issue opened 2023-12-08, community PR Dec 2024 closed as "practically unusable", first maintainer TV PR merged 2026-09-03 — [GitHub issue search](https://api.github.com/search/issues?q=repo:zoriya/Kyoo+%22android+tv%22&sort=updated)
- Reiverr 2.0 is a rewrite aimed at TVs that "still lacks some 1.0 features", with Android TV/webOS still future plans and Tizen the only TV platform shipped — [Reiverr README](https://github.com/aleksilassila/reiverr)
- Findroid, after years of development (4,272 stars), still lists Android TV as planned and does no transcoding — [Findroid README](https://raw.githubusercontent.com/jarnedemeulemeester/findroid/main/README.md)
- Wholphin reached 3,038 stars and ~1,887 commits within 13 months of creation (Sept 2025 → Oct 2026) by building only an Android TV client on the Jellyfin API with ExoPlayer+ASS and MPV engines — [GitHub API](https://api.github.com/repos/damontecres/Wholphin); [Wholphin README](https://github.com/damontecres/Wholphin)
- Streamyfin (5,266 stars) ships its own in-repo native `mpv-player` and `exoplayer-player` modules plus TV-specific modules (tv-recommendations, tv-search, tv-user-profile) on top of the Jellyfin TypeScript SDK — [Streamyfin modules](https://github.com/streamyfin/streamyfin/tree/develop/modules)
- The official Jellyfin Android TV app's attempt at libass took from April 2025 (first merge) to Oct 2025 (removed from release because it "can't be turned on") and is still being iterated in 2026 — [GitHub PR search](https://api.github.com/search/issues?q=repo:jellyfin/jellyfin-androidtv+libass+is:pr&sort=updated); [PR #5032](https://api.github.com/repos/jellyfin/jellyfin-androidtv/pulls/5032)
- Dim: 4,126 stars but 161 open issues and no push since Sept 2025 — [GitHub API](https://api.github.com/repos/Dusk-Labs/dim)
- Olaris: no stable release since April 2022 — [selfhosting.sh](https://selfhosting.sh/apps/olaris/)
- jellyfin-web's JASSUB adoption and reversal took roughly 10 months (May 2023 → March 2024) — [GitHub issue search](https://api.github.com/search/issues?q=repo:jellyfin/jellyfin-web+jassub&sort=updated)
- Jellyfin 12.0 broke legacy auth and `/emby/` paths and requires plugin rebuilds, illustrating ongoing API churn a fork or shim must track — [Jellyfin 12.0 post](https://jellyfin.org/posts/jellyfin-release-12.0/)

### Inferences (effort and risk; these are estimates, not sourced figures)
- Option (c), new client layer on Jellyfin's API: Android TV client in Kotlin with jellyfin-sdk-kotlin, Media3 + ass-media, and an optional libmpv engine is on the order of one experienced Android developer for 3–6 months to a usable beta (Wholphin's trajectory: creation Sept 2025, Play Store listing and 3k stars by Oct 2026 as a reference). A web client with jassub is a similar scale (Jellyfin-Vue has been in progress for years, so scope control matters). Ongoing burden: track Jellyfin major releases (12.x) and Media3/libass dependency churn. Risk: low; arr compatibility is inherited for free.
- Option (b), fork Jellyfin: you inherit the full C#/.NET server, plugin ecosystem, arr compatibility and jellyfin-ffmpeg, and can add OIDC and server-side niceties. The hidden cost is that forking does not solve libass at all (it is a client issue) and you must merge upstream security fixes (12.0 and 12.2 shipped security fixes) indefinitely. Forking Kyoo instead gives you OIDC and libass-correct subtitle plumbing but a bus-factor-one codebase, a custom API, and a Jellyfin-shim to write for the arr apps.
- Option (a), new server from scratch: scanner, metadata pipeline (TMDB/TVDB/AniDB/Shoko), multi-user auth + OIDC, HLS/transcode orchestration with hwaccel, session/playback state, Jellyfin-compatible API shim for the arr apps, plus at least two clients. Based on Kyoo's history (project started 2019, v5 rewrite in 2026, still one maintainer, Android TV client only reaching master in late 2026), this is a multi-year effort for a small team, and most of it duplicates what Jellyfin already does without improving the actual pain point (ASS rendering on TVs).
- Recommended shape: (c) first, i.e. an Android TV + web client pair with libass (Media3+ass-media with libmpv fallback; jassub on web), speaking Jellyfin's API and using Jellyfin's existing font/attachment endpoints; keep (b) as a later option if OIDC or server features become blocking; avoid (a).

### Gaps
- No primary-source effort figures (developer-months, budgets) exist for any of these projects; estimates above are inferred from repo timelines and should be labeled as such in the report.
- No blog post or HN thread by a maintainer of Kyoo, Dim or Olaris explaining lessons learned was found; the only lesson signals are repo timelines and README caveats.
- Jellyfin's client-side font attachment/`/Videos/{id}/{mediaSourceId}/Attachments/{index}` endpoints were not verified in this pass; Kyoo's "embedded fonts" support suggests this is table stakes for a libass client and should be confirmed against api.jellyfin.org.
