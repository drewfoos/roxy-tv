# Build the client first; borrow Jellyfin's server design

The styled-subtitle failure you are fighting is a client problem, not a server problem, and that single fact should shape the whole project. Jellyfin 12.2 (current as of 5 October 2026) already does the two server-side things an anime library needs: it hands an ASS track plus its MKV font attachments to any client that declares it can render them, and it burns the track in with libass inside jellyfin-ffmpeg for any client that cannot. What is missing is a stable Android TV or Android mobile client that renders ASS at all: the stable Jellyfin Android TV app (**v0.19.10, 16 August 2026**) forces a server transcode for every ASS track, and the libass renderer exists only in the **0.20.0 betas (September 2026) behind a disabled-by-default developer toggle**. A from-scratch server would have to implement one path-based notification endpoint for Sonarr and Radarr and a full probe, decision, HLS, session and auth stack, and at the end it would face exactly the same client gap. The field evidence points the same way: Wholphin reached about 3,000 GitHub stars in 13 months by building only an Android TV client on Jellyfin's API, while Kyoo, the one actively maintained new-generation server, took from December 2023 to September 2026 to merge an Android TV client with a single developer, and Dim and Olaris are dead. The highest-return build is therefore an Android TV plus web client pair that speaks Jellyfin's API, renders ASS with the libass-android `ass-media` Media3 extension (with embedded libmpv as a second engine) and with jassub on the web, and relies on Jellyfin's existing font-attachment and burn-in paths. This report still gives you the complete reference designs, the exact integration contract, and a concrete server architecture with phased effort and risk, so you can build the server later if OIDC, server-authoritative subtitle policy, or a webhook-driven scanner turns out to matter enough to justify a multi-year effort.

## Jellyfin 12.x is current, but the 10.11 internals still describe it

The research notes disagree on versions and the disagreement needs resolving before anything else. The architecture notes, sourced from master-branch code and release posts through June 2026, say the stable line is 10.11.x (10.11.11 announced 6 June 2026) and that there is no Jellyfin 11, with the team "considering" dropping the "10." prefix so the next major would be 12.0 ([State of the Fin, Jan 2026](https://jellyfin.org/posts/state-of-the-fin-2026-01-06)). The later-dated libass and codec notes confirm that this happened: **Jellyfin 12.0 shipped on 7–8 September 2026** ("What would have been 10.12.0 is simply 12.0"), followed by 12.1 on 15 September and **12.2 on 5 October 2026**, with jellyfin-ffmpeg moving to upstream **FFmpeg 8.1** ([Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/); [jellyfin releases](https://github.com/jellyfin/jellyfin/releases)). Treat 12.2 as current. Everything the 10.11 architecture description says about the scanner, the EF Core data model, `StreamBuilder`, `DynamicHlsController`, `SessionManager` and the `MediaBrowser` auth scheme still applies, because 12.0 was the planned "10.12" and changed subtitle handling and legacy compatibility rather than the architecture. The 12.0-specific deltas that matter here are: subtitle writing now goes through SubtitleEdit, which removes the old SSA-to-ASS conversion that overwrote styles with a hardcoded Arial (fixed by PR #16744, merged 3 May 2026); subtitle settings became per-library; external subtitles can be embedded into MKV during transcoding; VobSub rendering moved to libbitsub; the legacy `/emby/` and `/mediabrowser/` URL prefixes were removed and the deprecated sign-in method was disabled; and 12.2 serves graphical subtitles as raw files with range support ([Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/); [jellyfin PR #16744](https://github.com/jellyfin/jellyfin/pull/16744); [jellyfin releases](https://github.com/jellyfin/jellyfin/releases)). One terminology rule applies throughout this report: any claim that "Jellyfin supports libass" means either server-side ffmpeg burn-in or a specific client (Jellyfin Desktop via mpv, Kodi, the web client via WebAssembly). It never means the stable Android TV app or the Android mobile app.

### How Jellyfin works internally, as the primary reference design

Jellyfin is a C#/.NET monolith descended from Emby 3.5.2, with an ASP.NET Core/Kestrel API layer, EF Core over SQLite for persistence (the library database migration finished in 10.11), and an external ffmpeg/ffprobe for every media operation; nothing links libav directly ([Jellyfin README](https://github.com/jellyfin/jellyfin); [10.11.0 release post](https://jellyfin.org/posts/jellyfin-release-10.11.0)). The solution's `Emby.*` and `MediaBrowser.*` project names are the inherited Emby layout and `Jellyfin.*` are post-fork additions; `MediaBrowser.Controller` holds interfaces, `Emby.Server.Implementations` the implementations, `MediaBrowser.Model` the DTOs shared with clients, `Emby.Naming` the filename parsers, and `MediaBrowser.MediaEncoding` the ffmpeg management ([Source tree docs](https://jellyfin.org/docs/general/contributing/source-tree/)).

**Library scan.** A scan is a scheduled task (`RefreshMediaLibraryTask`) that validates top-level `CollectionFolder`s, then recursively calls `Folder.ValidateChildren`; each path runs through a priority-ordered chain of `IItemResolver`s after `IResolverIgnoreRule` filtering, with `IMultiItemResolver`s grouping multi-version and multi-part files, and `ResolverHelper.SetInitialItemValues` populating the result ([LibraryManager.cs](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Library/LibraryManager.cs)). `Emby.Naming` supplies the regexes: Kodi-style `SxxExx`, `1x01`, "Episode N", anime-style `Series - 04` and `[04]`, date-based names, multi-episode ranges, `cd/dvd/part/pt/disc` stacking rules, and a long `CleanStringRegexes` list that strips `1080p`, `x265`, `WEB-DL` and similar tokens; subtitle sidecar extensions are `.ass .mks .sami .smi .srt .ssa .sub .sup .vtt` with flag tokens `forced/foreign`, `default`, `cc/hi/sdh` ([NamingOptions.cs](https://github.com/jellyfin/jellyfin/blob/master/Emby.Naming/Common/NamingOptions.cs)). Item IDs are deterministic: `GetNewItemId` normalizes the path, prefixes the type name and MD5-hashes it ([LibraryManager.cs](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Library/LibraryManager.cs)). The anime-relevant weakness is that absolute numbering is parsed syntactically (an `epnumber` with no season) but the mapping to seasons is delegated to whichever metadata provider wins, which is why forum users report default providers splitting absolute-numbered series into seasons and why Shokofin exists ([Jellyfin forum](https://forum.jellyfin.org/t-absolute-order-detection-with-no-season-id); [JellyWatch Shokofin guide](https://jellywatch.app/blog/shokofin-jellyfin-anime-plugin-anidb-complete-guide-2026)).

**Metadata.** `ProviderManager` is a registry of `IMetadataProvider`, `IImageProvider`, `IMetadataSaver` and `IExternalId` implementations, ordered per library by `MetadataFetcherOrder`/`LocalMetadataReaderOrder`, with refreshes flowing through a priority queue to a type-specific `IMetadataService` ([ProviderManager.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Providers/Manager/ProviderManager.cs)). NFO reading and writing is a built-in local provider (`MediaBrowser.XbmcMetadata`), TMDB is in core, and AniDB, AniList, Anisearch, Kitsu and Shokofin are plugins ([Plugins docs](https://jellyfin.org/docs/general/server/plugins/)).

**Probing.** `MediaEncoder.GetMediaInfo` runs `ffprobe -i {input} -print_format json -show_streams -show_chapters -show_format` (plus `-show_frames -only_first_vframe` for local video), normalizes the JSON into `MediaInfo`, and persists the per-track result as `MediaStreamInfo` rows at scan time; `EncoderValidator` enumerates encoders, decoders, filters and hwaccels at startup ([MediaEncoder.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs)). Font attachments are dumped per media source with `ffmpeg -dump_attachment:t "" -i file -t 0 -f null null` into a folder that doubles as libass's `fontsdir` and as the backing store for `GET /Videos/{itemId}/{mediaSourceId}/Attachments/{index}`; extraction is lazy, happening on first burn-in or first client request ([AttachmentExtractor.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.MediaEncoding/Attachments/AttachmentExtractor.cs); [MediaInfoHelper.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Helpers/MediaInfoHelper.cs)).

**Data model.** Every `BaseItem` subclass (Movie, Series, Season, Episode, Folder, and so on) is one `BaseItemEntity` row whose `Type` column holds the CLR type name and whose `Data` column holds a serialized blob for type-specific fields, with normalized side tables for media streams, chapters, provider IDs, images, people, item values, ancestors, trickplay info and per-user data; `PrimaryVersionId`/`OwnerId` link alternate versions and extras ([BaseItemEntity.cs](https://github.com/jellyfin/jellyfin/blob/master/src/Jellyfin.Database/Jellyfin.Database.Implementations/Entities/BaseItemEntity.cs)). `MediaStream` is the model that drives playback decisions: codec, profile, level, bit depth, pixel format, color transfer, Dolby Vision profile and flags, computed `VideoRangeType`, and the subtitle predicates `IsTextSubtitleStream`, `IsPgsSubtitleStream`, `IsExtractableSubtitleStream` ([MediaStream.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Entities/MediaStream.cs)). The `User` entity carries `SubtitleMode`, `SubtitleLanguagePreference`, `RememberSubtitleSelections`, `RemoteClientBitrateLimit`, `MaxParentalRatingScore`, `MaxActiveSessions` and navigation collections for `Permissions`, `Preferences` and `AccessSchedules` ([User.cs](https://github.com/jellyfin/jellyfin/blob/master/src/Jellyfin.Database/Jellyfin.Database.Implementations/Entities/User.cs)).

**Playback decision.** A client POSTs `/Items/{id}/PlaybackInfo` with a `DeviceProfile` (`DirectPlayProfiles`, `TranscodingProfiles`, `ContainerProfiles`, `CodecProfiles` with conditions, `SubtitleProfiles`, and bitrate caps defaulting to 8 Mbps) and the server-side `StreamBuilder` evaluates each `MediaSourceInfo`: zero failures means `DirectPlay`, only container or audio failures means `DirectStream` (remux), anything else means `Transcode`, with every failure recorded as a `TranscodeReason` flag ([DeviceProfile.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Dlna/DeviceProfile.cs); [StreamBuilder.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Dlna/StreamBuilder.cs)). Subtitles are resolved by `GetSubtitleProfile`, which tries `Embed` (only when not HLS-transcoding and the container supports it, true for MKV, false for TS and MP4), then `External` or `Hls` (`Hls` only for text streams under transcoding), and falls back to `Encode`, meaning burn-in ([StreamBuilder.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Dlna/StreamBuilder.cs)). The decisive detail for anime is `SupportsSubtitleConversionTo`: it returns false when the source codec is `ass`/`ssa` or the target is, so ASS can be delivered as-is to a client that lists `{Format:"ass", Method:"External"}` but can never be converted to WebVTT for HLS, and a client lacking that profile line forces burn-in ([MediaStream.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Entities/MediaStream.cs)). `MediaInfoHelper` then applies user policy (`EnableVideoPlaybackTranscoding`, `EnablePlaybackRemuxing`, the remote bitrate cap when the client is off-LAN), sets `SupportsDirectPlay/DirectStream/Transcoding`, builds `TranscodingUrl`, and stamps each subtitle stream's `DeliveryMethod` and `DeliveryUrl` and each attachment's `DeliveryUrl` ([MediaInfoHelper.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Helpers/MediaInfoHelper.cs)).

**Transcoding and HLS.** `DynamicHlsController` is "playlist first, segments lazily": `master.m3u8` advertises variants (`CODECS`, `VIDEO-RANGE`, `SUPPLEMENTAL-CODECS` for copied Dolby Vision or HDR10+, a `subs` subtitle group, trickplay image streams), `main.m3u8` lists every segment up front from the runtime or keyframes, and each `hls1/{playlist}/{segmentId}.{ts|mp4}` request either serves an existing file or restarts a single ffmpeg with `-f hls -hls_time N -hls_list_size 0 -start_number {segmentId}`, killing the previous job when the requested segment is behind the current one or more than `24/SegmentLength` segments ahead; `-copyts -avoid_negative_ts disabled` keeps timestamps monotonic across restarts ([DynamicHlsController.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/DynamicHlsController.cs); [DynamicHlsHelper.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Helpers/DynamicHlsHelper.cs)). `TranscodeManager` extracts attachments before a burn-in job, redirects stdin and stderr ("Must consume both stdout and stderr or deadlocks may occur"), tracks jobs by `PlaySessionId` and `DeviceId`, and garbage-collects them on a ping timeout of 10 s for progressive and 60 s for HLS ([TranscodeManager.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.MediaEncoding/Transcoding/TranscodeManager.cs)). `EncodingHelper` assembles per-vendor chains for VAAPI, QSV, NVENC/CUDA, AMF/D3D11/OpenCL, Vulkan, VideoToolbox and RKMPP; text-subtitle burn-in is `subtitles=f='<path>':fontsdir='<attachments>'` in the software path, and in hardware paths libass renders onto an `alphasrc` canvas that is `hwupload`ed and composited with `overlay_qsv`/`overlay_cuda`/`overlay_vaapi`/`overlay_vulkan` so decoded frames never leave the GPU ([EncodingHelper.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Controller/MediaEncoding/EncodingHelper.cs)). `SubtitleEncoder` extracts embedded tracks with `-c:s copy` for ass/ssa/srt/pgs/vobsub into a cache with `.meta` freshness sidecars and converts text formats with SubtitleEdit-derived writers ([SubtitleEncoder.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.MediaEncoding/Subtitles/SubtitleEncoder.cs)).

**Sessions and watched state.** `SessionManager` keeps an in-memory dictionary keyed by client, device and user; clients call `POST Sessions/Playing`, `Sessions/Playing/Progress` (jellyfin-web every 10 s and on pause/unpause/volume events), `Sessions/Playing/Stopped` and `Sessions/Playing/Ping`; progress writes `UserData` (position, play count, played), idle sessions are stopped after 5 minutes without a check-in, and remote control, SyncPlay and library-change pushes go over a websocket ([SessionManager.cs](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Session/SessionManager.cs); [PlaystateController.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/PlaystateController.cs); [playbackmanager.js](https://github.com/jellyfin/jellyfin-web/blob/master/src/components/playback/playbackmanager.js)). Sessions are not persisted; a restart forgets them and clients re-report.

**Auth and API.** The custom scheme parses `Authorization: MediaBrowser Client="…", Device="…", DeviceId="…", Version="…", Token="…"`; the legacy `X-Emby-Authorization`, `X-Emby-Token`, `X-MediaBrowser-Token` and `api_key` forms sit behind `EnableLegacyAuthorization`, and tokens resolve either to a Device row (a user session) or an ApiKey row (no user) ([AuthorizationContext.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Server.Implementations/Security/AuthorizationContext.cs)). Quick Connect issues a 6-digit code and a 64-hex secret with a 10-minute expiry so a TV can be authorized from a phone ([QuickConnectManager.cs](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/QuickConnect/QuickConnectManager.cs)). The OpenAPI document is generated from the ASP.NET controllers and the TypeScript and Kotlin SDKs are generated from it, with SDK 1.0.0 mapping to Jellyfin 12.x ([TS SDK README](https://github.com/jellyfin/jellyfin-sdk-typescript)). The one architectural lesson Jellyfin paid for dearly is persistence: the move from scattered raw SQLite calls to EF Core took "six months of development and six months of release candidate testing," four further point releases with over 100 changes, and produced migration failures and client-side-enumeration performance regressions ([State of the Fin, Jan 2026](https://jellyfin.org/posts/state-of-the-fin-2026-01-06); [10.11.0 release post](https://jellyfin.org/posts/jellyfin-release-10.11.0)).

### How Plex works, and where its design diverges

Plex Media Server is a single closed-source native process owning a SQLite library (`com.plexapp.plugins.library.db`) whose community-documented shape is `metadata_items` → `media_items` → `media_parts` → `media_streams`, with watch state in `metadata_item_settings` keyed by `account_id` and the item `guid` rather than by primary key, which is why re-matching an item preserves its state ([Plex forums: query data](https://forums.plex.tv/t/howto-query-data-from-plex-on-a-mac/11636.md); [Plex forums: watched status](https://forums.plex.tv/t/sqlite3-access-to-watched-status/81143.md)). Metadata comes from Plex's own cloud agents (`tv.plex.agents.movie`, `tv.plex.agents.series`) that store `plex://` GUIDs plus external `tmdb://`, `tvdb://`, `imdb://` children exposed via `includeGuids=1`, while the legacy agent framework is a sandboxed, end-of-life Python 2.7 runtime that still carries anime users through HAMA ([python-plexapi library.py](https://raw.githubusercontent.com/pkkid/python-plexapi/master/plexapi/library.py); [Plex forums: dev.plexapp.com](https://forums.plex.tv/t/what-happened-to-dev-plexapp-com/849957.md); [HAMA thread](https://forums.plex.tv/t/rel-http-anidb-metadata-agent-hama/40470?page=97)). The transcoder is a private FFmpeg fork being rebuilt on FFmpeg 6.1 since mid-2025, with a separate licensed `EasyAudioEncoder` helper, and subtitle burn-in is single-threaded ([Transcoder Upgrade preview](https://forums.plex.tv/t/transcoder-upgrade-forum-preview/924241); [Plex forums: subtitles slowing transcoding](https://forums.plex.tv/t/subtitles-slowing-down-transcoding/800198.md)).

The playback decision model is the most instructive contrast. Plex matches server-side XML client profiles (`Resources/Profiles/*.xml`, with `DirectPlayProfiles`, `CodecProfiles` with `UpperBound`/`Match` limitations, and `TranscodeTargets`) by HTTP header or DLNA description, and native apps augment them at runtime through an undocumented `X-Plex-Client-Profile-Extra` header whose directives the server parser sometimes rejects before silently falling back to a "Web" profile; a developer post states that for Plex's own apps the client makes the direct-play versus transcode decision before asking the server ([Plex forums: writing profiles](https://forums.plex.tv/t/writing-profiles-for-dlna-devices/38060); [Plex forums: speeding up CentOS VM](https://forums.plex.tv/t/speeding-up-centos-vm/357390); [Plex forums: H265 transcoded](https://forums.plex.tv/t/why-does-h265-video-get-transcoded-when-only-audio-eac3-is-incompatible/781159.md)). Decisions are only visible by grepping debug logs for "reached decision" ([Plex forums: always transcoding](https://forums.plex.tv/t/media-server-always-transcoding/787669.md)). Identity is entirely cloud-side: the PIN flow runs against `plex.tv/api/v2/pins`, sharing and Plex Home are plex.tv objects, and since **29 April 2025 remote playback requires Plex Pass ($6.99/month, $69.99/year) or a per-user Remote Watch Pass**, rolled out to Roku in November 2025 and to other TV apps and third-party API clients in 2026 ([Plex forums: authenticating](https://forums.plex.tv/t/authenticating-with-plex/609370); [BetaNews, March 2025](https://betanews.com/2025/03/19/plex-2025-price-changes-remote-streaming-new-subscription/); [Plex forums: Roku remote streaming](https://forums.plex.tv/t/changes-coming-to-remote-streaming-on-roku/933671/1)). Webhooks and hardware transcoding are Plex Pass features, and the relay fallback is capped at 1–2 Mbps ([support.plex.tv: Webhooks](https://support.plex.tv/articles/115002267687-webhooks/); [Plex forums: relay bandwidth](https://forums.plex.tv/t/remote-access-bandwidth-limit/586227)). The lessons a new server should take from Plex are concrete: key user state by stable external GUIDs, keep metadata providers out of process rather than embedding an interpreter, make the decision engine server-authoritative and return its reasons in the API response, and never gate LAN or WAN playback on a cloud entitlement.

## ASS fails at the client; the server already renders it with libass

Jellyfin's server knows exactly what ASS is. The codec-support documentation classifies ASS/SSA as "Formatted Text", supported in MKV and not in MP4 or TS, and says subtitles that need transcoding "can be converted into another format that is supported, or burned into the video," with burn-in "the most intensive method of transcoding" ([Jellyfin Codec Support](https://jellyfin.org/docs/general/clients/codec-support/)). Because `SupportsSubtitleConversionTo` refuses ASS on both sides, the server's only two outcomes for an ASS track are "deliver as-is to a client that declared `External` or `Embed` for `ass`" or "burn in with libass" ([MediaStream.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Entities/MediaStream.cs)). The whole question is therefore which clients declare and honour that capability, and the honest answer per client as of 13 October 2026 is below.

The Android TV history deserves spelling out because it is the crux of your decision. An experimental libass direct-play path (#4630) and an overlay-rendering change (#4685) landed during the 0.19 cycle, were stripped from non-development builds (#4876) and then removed entirely (#5032) before 0.19.0 stable shipped, with the maintainer stating in November 2025 that libass "was held back from 0.19 because of performance problems" and that media3's own SSA support is "near non-existent" ([v0.19.0 release](https://github.com/jellyfin/jellyfin-androidtv/releases/tag/v0.19.0); [#2875](https://github.com/jellyfin/jellyfin-androidtv/issues/2875)). The reintroduction depended on upstream library fixes: libass-android issue #57 documented moving signs that "jump from a position to another one" on a Shield Pro because render timing does not align with video frame timing (an androidx/media limitation), with OpenGL overlay mode "significantly reducing stuttering," v0.4.0 fixing several issues, and a separate Media3 font-attachment bug tracked as androidx/media#2536; the issue closed on 8 March 2026 with the note that the media-side timing issue remains open ([libass-android #57](https://github.com/peerless2012/libass-android/issues/57)). Google will not solve this upstream: the Media3 maintainer declared the libass native-decoder PR "unlikely to merge" because "the maintenance burden is likely to be too high," and as of 18 September 2026 the recommendation is to use libass-android instead ([androidx/media PR #2324](https://github.com/androidx/media/pull/2324)).

Server-side burn-in has its own well-documented failure modes that a new design should avoid. Because attachment extraction is lazy, a client path that starts a transcode without triggering it leaves the attachments folder empty and ffmpeg falls back to a default font; the reporter's workaround was to play the file once in a browser first, and the issue was closed stale rather than fixed ([jellyfin #13914](https://github.com/jellyfin/jellyfin/issues/13914)). Jellyfin ships no fonts, so CJK and Arabic scripts render as boxes unless the server has `fonts-noto-cjk` or similar installed, and burn-in ignores client font size and colour settings because the server renders them ([jellyfin-web #1670](https://github.com/jellyfin/jellyfin-web/issues/1670); [#5507](https://github.com/jellyfin/jellyfin-androidtv/issues/5507); [forum](https://forum.jellyfin.org/t-changing-font-size-for-transcoded-subtitles)). External `.ass` sidecars cannot use fonts attached inside the MKV, which is why the community recommendation is to mux fonts and ASS into the container ([forum](https://forum.jellyfin.org/t-subtitle-does-not-display-correctly); [thewiki.moe](https://thewiki.moe/guides/quality/)). A 10.10.0 regression ("libass: Failed to load fontconfig fonts") broke ASS on web, Android and Roku until 10.10.5 ([jellyfin-web #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)), and the "burn in all complex formats" and "always burn in subtitle when transcoding" options are per-client settings with no server-wide default ([forum](https://forum.jellyfin.org/t-enable-always-burn-in-subtitle-when-transcoding-by-default)). On the positive side, 10.11 made ASS rendering under hardware transcoding more accurate and 12.0 removed the SSA style-loss bug ([10.11.0 release post](https://jellyfin.org/posts/jellyfin-release-10.11.0/); [Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/)).

## The arrs need one path-based notification, a webhook, and matching mounts

Current versions are Sonarr v4.0.20 and Radarr v6.4.4 (both 16 September 2026).

Sonarr and Radarr's built-in Emby/Jellyfin connection uses only four calls: `GET /System/Configuration` to test, `POST /Notifications/Admin`, `GET /Items?recursive=true&includeItemTypes=Series&fields=Path,ProviderIds&years=` to find the series path by TVDB/IMDb/TMDb ID, and **`POST /Library/Media/Updated` with `{"Updates":[{"Path":"…","UpdateType":"…"}]}`**, sending both `X-MediaBrowser-Token: <ApiKey>` and `Authorization: MediaBrowser Token="<ApiKey>"` on every request ([Sonarr MediaBrowserProxy.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/MediaBrowser/MediaBrowserProxy.cs)). On the receiving side Jellyfin's handler reads only `Path`, calls `_libraryMonitor.ReportFileSystemChanged(path)` and returns 204; `Library/Movies/Updated` and `Library/Series/Updated` match by provider ID, and `POST /Library/Refresh` triggers a full validation ([jellyfin LibraryController.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/Jellyfin.Api/Controllers/LibraryController.cs)). Because this is path-based, the server must see the same mount paths Sonarr sees or implement a prefix-replace path mapping.

The better integration for a new server is the generic Webhook connect, which carries IDs so the scanner never parses filenames. Sonarr's `eventType` is a string enum (`Test, Grab, Download, Rename, SeriesAdd, SeriesDelete, EpisodeFileDelete, Health, ApplicationUpdate, HealthRestored, ManualInteractionRequired`), and the `Download` payload (import and upgrade) includes `series` (`Id, Title, TitleSlug, Path, TvdbId, TvMazeId, TmdbId, ImdbId, MalIds[], AniListIds[], Type, Year, …`), `episodes[]` (`Id, EpisodeNumber, SeasonNumber, Title, AirDateUtc, TvdbId, …`), `episodeFile` (`Path` = `series.Path + RelativePath`, `Quality`, `ReleaseGroup`, `SceneName`, `Size`, `Languages`, `MediaInfo{AudioChannels, AudioCodec, AudioLanguages[], Height, Width, Subtitles[], VideoCodec, VideoDynamicRangeType}`, `SourcePath`), `isUpgrade`, and `deletedFiles[]`; `Rename` carries `renamedEpisodeFiles` with previous and new paths ([Sonarr WebhookEventType.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookEventType.cs); [WebhookBase.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookBase.cs); [WebhookSeries.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookSeries.cs); [WebhookEpisodeFile.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookEpisodeFile.cs)). Radarr's equivalents are `Grab, Download, Rename, MovieAdded, MovieDelete, MovieFileDelete, Health, HealthRestored, ApplicationUpdate, ManualInteractionRequired, Test`, with `movie` (`TmdbId, ImdbId, FolderPath, Title, Year, …`) and `movieFile` (`Path, Quality, ReleaseGroup, MediaInfo, …`) ([Radarr WebhookBase.cs](https://raw.githubusercontent.com/Radarr/Radarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookBase.cs); [WebhookMovie.cs](https://raw.githubusercontent.com/Radarr/Radarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookMovie.cs)). Two caveats from the notes: the JSON property casing (camelCase in practice) was not confirmed from the serializer settings, and `WebhookEpisode` carries no absolute episode number, so absolute numbers must come from the filename's `- 001 -` token or a server-side lookup. Prowlarr needs nothing from the media server at all; it only syncs indexers into Sonarr and Radarr ([Servarr wiki: Prowlarr quick start](https://raw.githubusercontent.com/Servarr/Wiki/master/prowlarr/quick-start-guide.md)).

File naming follows TRaSH. The anime episode format is `{Series CleanTitleWithoutYear} {(Series Year)} - S{season:00}E{episode:00} - {absolute:000} - {Episode CleanTitle:90}` plus quality, dynamic range, `[10bit]`, codec, audio and language tokens and `-{Release Group}`, yielding names like `The Series Title! (2010) - S01E01 - 001 - Episode Title 1 [iNTERNAL HDTV-720p v2][HDR10][10bit][x264][DTS 5.1][JA]-RlsGrp`; series folders for Jellyfin use `[tvdbid-{TvdbId}]` (TVDb only, since "Jellyfin does not support IMDb IDs for shows") and seasons use `Season 01` ([TRaSH Sonarr naming](https://trash-guides.info/Sonarr/Sonarr-recommended-naming-scheme/)). Radarr's Jellyfin variants are `[imdbid-{ImdbId}]` or `[tmdbid-{TmdbId}]` in both folder and file names, and TRaSH warns that folder IDs are frozen at add time so the filename ID is the fresher key ([TRaSH Radarr naming](https://trash-guides.info/Radarr/Radarr-recommended-naming-scheme/)). The storage layout is one `/data` volume shared by the download client, Sonarr, Radarr and the media server, with downloads in `/data/torrents/{tv,movies}` (download client categories) and the library in `/data/media/{tv,movies}`; hard links are on by default, cost no space, require the same filesystem, and fall back to copying when they fail ([TRaSH Docker folder structure](https://trash-guides.info/File-and-Folder-Structure/How-to-set-up/Docker/); [Servarr wiki: Sonarr FAQ](https://raw.githubusercontent.com/Servarr/Wiki/master/sonarr/faq.md)). Your server container must mount `/data` (or at least `/data/media`) at the same path, index only the `/data/media` tree, and never modify a file in place, because the twin in `/data/torrents` is still seeding; upgrades arrive as a delete-plus-add in one `Download` event.

Bazarr, if you add it, writes sidecars as `<video basename>.<lang>[.forced|.hi|.cc|.sdh][.custom-tags].srt`, swapping the extension to `.ass` or another format for non-SRT providers; `forced` and the hearing-impaired tag are mutually exclusive, the HI suffix is configurable among `hi`, `cc` and `sdh`, "single language" mode drops the language suffix entirely, and files may land in a configured sub-folder; `ignore_ass_subs` exists for embedded ASS ([bazarr core.py](https://raw.githubusercontent.com/morpheus65535/bazarr/master/custom_libs/subliminal_patch/core.py); [bazarr config.py](https://raw.githubusercontent.com/morpheus65535/bazarr/master/bazarr/app/config.py)). A parser of the form `^(base)(?:\.(lang))?(?:\.forced)?(?:\.(hi|cc|sdh))?(?:\.(tags))?\.(srt|ass|ssa|vtt|sub|idx|sup)$` is my inference from that code and should be validated against your Bazarr version. Bazarr mounts only `/data/media`, so subtitles appear asynchronously after the video and the server needs a filesystem watcher, not just the Sonarr webhook, to pick them up.

## Anime codecs: Hi10P and libass burn-in are CPU problems a GPU cannot fix

Anime releases are overwhelmingly MKV with HEVC or AVC video, "typically in 8-bit, or 10-bit for high-quality anime encodes," ASS subtitles with fonts "embedded in MKV as attachments or shipped in a separate folder," and lossless audio in DTS-HD MA, FLAC or TrueHD alongside lossy AAC, MP3 and Opus; the main community quality guide, current as of August 2026, does not mention AV1 at all ([thewiki.moe Quality guide](https://thewiki.moe/guides/quality/)). Release sizes run from about 1.3 GB per WEB-DL episode to about 6 GB per remux ([thewiki.moe Quality guide](https://thewiki.moe/guides/quality/)). Because MP4 and TS cannot carry ASS or PGS, any HLS transcode to a TS or fMP4 target must either extract text subtitles out-of-band or burn them in ([Jellyfin Codec Support](https://jellyfin.org/docs/general/clients/codec-support/)).

**Hi10P is the one codec with no escape.** Jellyfin's documentation states that "hardware decoding of 10-bit H.264/AVC (High 10 profile) is not supported on Intel, NVIDIA, or AMD GPUs. It is only supported on Apple Silicon and Rockchip," and recommends converting such files to HEVC Main 10 ([Jellyfin Hardware Acceleration](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/)); NVIDIA lists H.264 10-bit as "Blackwell and newer" but "not currently enabled in Jellyfin" ([Jellyfin NVIDIA HWA](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/nvidia/)). On the client side the Shield's hardware decoder has never supported Hi10P, and the Kodi wiki states that no hardware decoders exist and none are planned ([NVIDIA Shield forum](https://www.nvidia.com/en-us/geforce/forums/shield-tv/9/271263/nvidia-shield-atvkodi10bit-mkv-playback/); [Kodi Wiki: Hi10P](https://kodi.wiki/view/Archive:Hi10P)). The consequence is that a Hi10P x264 release is CPU-decoded on the client or CPU-decoded on the server before hardware encoding; the CPU, not the GPU, bounds Hi10P stream count. HEVC Main10 is broadly hardware-decoded. AV1 hardware decode is confirmed for Google TV Streamer (MediaTek MT8696), Onn 4K Pro (Amlogic S905X4) and Fire TV Stick 4K Max 2nd gen, requires Android TV 10 or later in Jellyfin's matrix, and is absent on the A15-based Apple TV 4K and (per conflicting sources) the 2019 Shield ([Jellyfin Codec Support](https://jellyfin.org/docs/general/clients/codec-support/); [androidtv-guide: Google TV Streamer](https://androidtv-guide.com/streaming-gaming/google-tv-streamer); [AFTVnews AV1 list](https://www.aftvnews.com/list-of-fire-tvs-fire-tv-sticks-and-fire-tv-smart-tvs-that-support-av1-video-decoding/); [FlatpanelsHD: Apple TV AV1](https://www.flatpanelshd.com/news.php?subaction=showfull&id=1694598394)). On the server, AV1 decode starts at Intel Tiger Lake and NVIDIA Ampere, and AV1 encode at Intel Arc A-series/Meteor Lake and NVIDIA Ada ([Jellyfin Intel HWA](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/intel/); [Jellyfin NVIDIA HWA](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/nvidia/)).

**Audio passthrough is device-bound.** Jellyfin's client table shows FLAC, AAC, EAC3 and Opus supported across browsers, Android, Android TV, iOS and Roku, DTS unsupported in all browsers and on iOS, and TrueHD absent from the table entirely ([Jellyfin Codec Support](https://jellyfin.org/docs/general/clients/codec-support/)). Among Android TV boxes, the Shield TV Pro is the only one with TrueHD and DTS passthrough; Onn 4K Pro and Fire TV Stick 4K Max cap Atmos at lossy DD+ ([JellyWatch device comparison](https://jellywatch.app/blog/best-streaming-device-jellyfin-4k-hdr-av1-2026)). The 0.20.0-beta.3 Android TV app added passthrough auto-detection with overrides ([jellyfin-androidtv releases](https://github.com/jellyfin/jellyfin-androidtv/releases)). Plex supports DTS and TrueHD passthrough only with full Direct Play, never Direct Stream or transcode ([Plex: media formats](https://support.plex.tv/articles/203824396-what-media-formats-are-supported/)).

**Burn-in is CPU-bound even with hardware transcoding.** The actual QSV command Jellyfin emits renders ASS on a transparent canvas, `alphasrc=s=1920x1080:r=23.976,format=bgra,subtitles=f=…:alpha=1:sub2video=1:fontsdir=…,hwupload=derive_device=qsv:extra_hw_frames=64[sub]`, then composites with `[main][sub]overlay_qsv=eof_action=pass:repeatlast=0` ([Jellyfin forum: QSV burn-in](https://forum.jellyfin.org/t-the-burn-in-subtitles-will-become-semi-transparent-when-enable-hardware-acceleration)). Only the compositing and scaling run on the GPU; libass still rasterizes every frame on the CPU at output canvas size, which is why Jellyfin's docs list "subtitle burn-in" as a stage that may not be GPU-accelerated, why a moderator describes it as "two transcodings happen at once," and why Plex's burn-in is single-threaded ([Jellyfin Hardware Acceleration](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/); [Jellyfin forum: subtitle issues](https://forum.jellyfin.org/t-solved-subtitle-issues?page=2); [Plex forums](https://forums.plex.tv/t/subtitles-slowing-down-transcoding/800198.md)). A Raspberry Pi 5 went from 5–30% to near 100% CPU when burning PGS ([Jellyfin forum](https://forum.jellyfin.org/t-performance-issue-with-subtitles)). No source benchmarks libass milliseconds per frame on 2025–2026 hardware, so size the CPU conservatively: Jellyfin says "a GPU is always recommended, where even a basic Intel iGPU can handle as much load as a Ryzen 5800X," and a vendor comparison rates an N100 at 3–4 concurrent 4K HEVC transcodes and an Arc A380 at 6–8, but those figures exclude subtitle load, so an N305-class or desktop Core CPU paired with an Arc A310/A380 is the defensible shape for a burn-in-heavy anime server ([Jellyfin Hardware Selection](https://jellyfin.org/docs/general/administration/hardware-selection/); [JellyWatch GPU guide](https://jellywatch.app/blog/best-gpu-for-jellyfin-transcoding-2026-intel-nvidia-amd)). Hardware caveats that bite anime servers specifically: consumer GeForce NVENC sessions are capped by driver version (3/5/8/12), Arc B-series needs kernel 6.12+ and mandatory Resizable BAR, and an AMD VAAPI bug in Plex turns 10-bit HEVC with ASS burn-in grayscale ([Jellyfin Known Issues](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/known-issues/); [Plex forum bug](https://forums.plex.tv/t/bug-video-renders-black-and-white-chroma-lost-when-burning-in-ass-subtitles-with-amd-vaapi-hardw/940505)).

**Ordered chapters and segment linking are unsupported everywhere.** Plex states that "ordered chapters (custom orders, and also segment linking to external files) is not" supported, Jellyfin's feature request is open, and the root cause is FFmpeg ticket #3123, open for over a decade; mpv supports ordered chapters natively, VLC only partially ([Plex forums](https://forums.plex.tv/t/mkv-ordered-chapters-support/3839?page=2); [features.jellyfin.org #390](https://features.jellyfin.org/posts/390/support-mkv-ordered-chapters-segment-linking); [FFmpeg trac #3123](https://fftrac-bg.ffmpeg.org/ticket/3123); [mpv-segment-linking](https://github.com/CogentRedTester/mpv-segment-linking)). Because every server probes and transcodes through FFmpeg, no from-scratch server fixes this without a custom demux layer; the practical rule is to remux segment-linked releases into self-contained episodes with MKVToolNix.

## Every working alternative is a client; the server alternatives are dead or one-person

**Kodi + Jellyfin for Kodi / JellyCon** is the only Android TV option where MKV font-attachment loading is documented in merged source: Kodi 20 moved subtitle rendering to libass and PR #19535 extracts muxed fonts into the user font directory ([Kodi forum](https://forum.kodi.tv/showthread.php?tid=364572); [xbmc PR #19535](https://github.com/xbmc/xbmc/pull/19535)). Its cost is account handling: the add-on "doesn't natively handle multiple accounts," so multi-user means one Kodi profile per Jellyfin user; watched and resume state sync two-way in near real time via websocket and the Kodi Sync Queue plugin, but with a history of regressions, and external-player playback does not sync state ([Jellyfin docs: Kodi](https://jellyfin.org/docs/general/clients/kodi); [jellyfin-kodi #932](https://github.com/jellyfin/jellyfin-kodi/issues/932)). JellyCon is the thin, user-switchable alternative ([jellycon](https://github.com/jellyfin/jellycon)). **Wholphin** (Android TV and Fire TV, GPL-2.0, created September 2025) runs ExoPlayer with optional libass-android or mpv "for direct playback of almost any media, with strong SSA/ASS subtitle support," reached about 3,000 stars and 1,900 commits in 13 months, and is on Google Play; its libass integration broke ASS entirely in March 2026 until a lifecycle fix in May ([Wholphin README](https://github.com/damontecres/Wholphin); [Wholphin #1049](https://github.com/damontecres/Wholphin/issues/1049)). **Streamyfin** (Expo/React Native, MPL-2.0, about 5,300 stars) uses mpv on all platforms via in-repo native modules and ships TV build targets, with v0.54.1 on 2 June 2026 ([Streamyfin README](https://raw.githubusercontent.com/streamyfin/streamyfin/develop/README.md); [Streamyfin modules](https://github.com/streamyfin/streamyfin/tree/develop/modules)). **Findroid** renders ASS through mpv on phones but lists Android TV as planned and does no transcoding ([Findroid README](https://raw.githubusercontent.com/jarnedemeulemeester/findroid/main/README.md)). The **Jellyfin Thor fork** sideloads alongside the official app with libass 0.17.5, a Media3 FFmpeg decoder, an mpv option and Shield Hi10P fallbacks, and is "not supported by the Jellyfin team" ([thor2002ro/jellyfin-androidtv](https://github.com/thor2002ro/jellyfin-androidtv)). The **official 0.20 beta** is covered above; a news article expects the betas to "officially end in the next month or so, with no set release dates" ([New In Linux](https://www.newinlinux.com/jellyfin-android-tv-finamp-clients-are-about-to-get-big-updates/)).

**Kyoo** is the only actively maintained new-generation server: TypeScript, Go and Python, GPL-3.0, about 2,500 stars, pushed 12 October 2026, with lazy HLS transcoding and hardware acceleration in its Go transcoder, ASS with embedded fonts "including on web and Chromecast," OIDC with any compliant provider, and Android TV PRs merged on master in September–October 2026 but no released TV client; it is "developed by one person," its v5 rewrite temporarily dropped watch-list sync and offline downloads, and it has no Sonarr or Radarr integration ([Kyoo README](https://raw.githubusercontent.com/zoriya/Kyoo/master/README.md); [GitHub API](https://api.github.com/repos/zoriya/Kyoo); [Kyoo Android TV issues](https://api.github.com/search/issues?q=repo:zoriya/Kyoo+%22android+tv%22&sort=updated)). **Seanime** (Go, GPL-3.0) is an AniList-driven downloader and desktop libmpv player with torrent streaming, no Android TV, no multi-user and no arr integration ([Seanime README](https://raw.githubusercontent.com/5rahim/seanime/main/README.md)). **Dim** (Rust) last pushed September 2025 with 161 open issues and **Olaris** (Go) has had no stable release since April 2022 ([GitHub API: Dim](https://api.github.com/repos/Dusk-Labs/dim); [selfhosting.sh: Olaris](https://selfhosting.sh/apps/olaris/)). **Shoko + Shokofin** is a metadata layer on Jellyfin (AniDB-hash matching, structure independent of filenames), actively pushed as of October 2026, and compatible with any client above ([Shokofin](https://api.github.com/repos/ShokoAnime/Shokofin)).

**Plex** now costs at least $69.99/year server-side for remote streaming, its Android TV app burns complex ASS by default, its mobile and Apple TV apps regressed after dropping libmpv, and only Plex HTPC (libmpv as a swappable `mpv-2.dll`) renders ASS faithfully among first-party clients ([plex.tv/plans](https://www.plex.tv/plans/); [Plex forums: bring back subtitle support](https://forums.plex.tv/t/plans-to-bring-back-subtitle-support/943302); [Plex HTPC guide](https://forums.plex.tv/t/plex-htpc-guide-windows/857522.md)). **Emby** ships a libass JNI renderer on Android that fails on real anime tracks, gates hardware transcoding behind Premiere ($4.99/month, $119 lifetime), and staff admitted in 2018 that burned-in fonts "can be slightly different" with no fix ([Emby topic 136069](https://emby.media/community/topic/136069-ass-subtitles-dont-render-on-android-tv); [emby.media/premiere](https://emby.media/premiere.html); [Emby: ASS font style](https://emby.media/community/index.php?/topic/62113-ass-font-style-with-transcoding/)). One genuine Jellyfin gap worth noting: it "currently has no native external authentication support," and the community SSO plugins mostly work only in a browser with Quick Connect as the native-app workaround ([Jellyfin discussion #16470](https://github.com/orgs/jellyfin/discussions/16470); [Pocket ID Jellyfin guide](https://pocket-id.org/docs/client-examples/jellyfin)).

## A from-scratch design: Sonarr-fed scanner, explainable decisions, libass only as last resort

The project is called **Roxy TV**: Roxy Server is the backend, the Roxy TV app is the Android TV client, and Roxy Web is the browser client. One naming note before the design: the bare name "roxy" is already used by several reverse-proxy projects and a GitHub user, so the GitHub organisation, Docker images and package names should be namespaced (for example `roxy-media` or `roxytv`). If you build Roxy Server anyway, the design below takes what Jellyfin and Plex got right and avoids what each got wrong.

**Server stack.** Three defensible options exist. C#/.NET lets you reuse SubtitleEdit (which Jellyfin 12 now uses for subtitle writing), SkiaSharp and the Jellyfin model vocabulary, at the cost of a heavy runtime. Go gives a single static binary and an existing reference transcoder in Kyoo's gocoder (lazy HLS, VAAPI/QSV/CUDA, usable outside Kyoo) ([pkg.go.dev gocoder](https://beta.pkg.go.dev/github.com/zoriya/kyoo/transcoder)). Rust has no living media-server ecosystem to borrow from (Dim is dead). My recommendation is Go for Roxy Server with a thin TypeScript layer only if you want to share types with Roxy Web. Whatever the language, shell out to jellyfin-ffmpeg's portable builds (v8.1.3-1, 27 September 2026, Linux amd64/arm64, macOS and Windows) rather than vendoring FFmpeg: you inherit Jellyfin's tested hwaccel matrix, libass burn-in, the `sub2video` and attachment-filename fixes, and because you shell out rather than link, the GPL build does not contaminate your code ([jellyfin-ffmpeg releases](https://api.github.com/repos/jellyfin/jellyfin-ffmpeg/releases/latest); [jellyfin-ffmpeg](https://github.com/jellyfin/jellyfin-ffmpeg)). Use SQLite with a real relational schema from day one, with FTS for titles (Plex's pattern) and foreign keys enforced; Jellyfin's half-decade of EF Core retrofit pain and Plex's growing-database slowness both argue for deciding the schema before writing the scanner ([10.11.0 release post](https://jellyfin.org/posts/jellyfin-release-10.11.0); [Plex forums: slow library](https://forums.plex.tv/t/slow-library-performance-due-to-increasingly-growing-database/740511/1)).

**Data model.** Adopt the four-level shape both incumbents converged on: a logical `Item` (movie, series, season, episode, with `ProviderIds` as a map keyed `Tmdb`, `Tvdb`, `Imdb`, `AniDB`, `MyAnimeList`, `AniList`), one or more `MediaSource` versions, one or more `MediaPart` files per source (for stacking), and `MediaStream` rows per track carrying the full ffprobe-derived set Jellyfin stores (codec, profile, level, bit depth, pixel format, colour transfer and primaries, Dolby Vision profile and RPU/EL/BL flags, HDR10+ flag, channel layout, language, default/forced/SDH flags, and for subtitles the text-versus-image classification). Add a first-class `Attachment` table (font name, MIME, extracted path, extracted-at) populated at scan time rather than lazily, which directly removes the #13914 class of bug. Key per-user watch state by the item's stable external GUID rather than its row ID, so re-matching or re-importing preserves history as Plex does ([Plex forums: watched status](https://forums.plex.tv/t/sqlite3-access-to-watched-status/81143.md)). Make series ordering explicit: store aired (TVDb), absolute and AniDB numbering side by side on each episode, with a per-user or per-library display preference, instead of leaving the choice to whichever metadata provider wins. Users need an id, a name, an admin flag and an avatar, plus per-device tokens, library-scoped access, parental rating caps, remote bitrate caps and per-user subtitle preferences (mode, language, remember-selection) mirroring Jellyfin's `User` entity ([User.cs](https://github.com/jellyfin/jellyfin/blob/master/src/Jellyfin.Database/Jellyfin.Database.Implementations/Entities/User.cs)).

**Scanner driven by webhooks and IDs, not filenames.** The primary ingest is the Sonarr/Radarr Webhook connect: on `Download`, create or update the item from `series.tvdbId`/`tmdbId`/`imdbId`/`malIds`/`aniListIds` and `episodes[].seasonNumber`/`episodeNumber`, attach the file from `episodeFile.path`, and handle `deletedFiles[]` in the same transaction for upgrades; on `Rename`, re-key by `renamedEpisodeFiles` previous-to-new paths without re-probing; on `EpisodeFileDelete`/`MovieFileDelete`/`SeriesDelete`/`MovieDelete`, remove accordingly ([Sonarr WebhookBase.cs](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/NzbDrone.Core/Notifications/Webhook/WebhookBase.cs)). Resolve AniDB IDs by reverse lookup in Fribb/anime-lists, whose `anime-list-full` entries carry `anidb_id`, `anilist_id`, `mal_id`, `tvdb_id`, `themoviedb_id`, `imdb_id` and TVDb/TMDb `season` and `episode_offset` fields ([Fribb/anime-lists README](https://raw.githubusercontent.com/Fribb/anime-lists/master/README.md)). Run a reconciliation poll against `/api/v3/series`, `/api/v3/episodefile`, `/api/v3/movie` and `/api/v3/moviefile` with `X-Api-Key` to catch missed webhooks, and keep a filesystem watcher on `/data/media` for Bazarr sidecars and manual drops. Filename regexes (TRaSH's `[tvdbid-…]`, `[tmdbid-…]`, `- 001 -`, `[10bit]`, `[JA]`, `-Group`) become a fallback for the no-webhook case, not the primary path. Also implement `POST /Library/Media/Updated` and `POST /Library/Refresh` so the built-in Emby/Jellyfin connect works unchanged. Probe with ffprobe at ingest (JSON, streams, chapters, format, first video frame) and extract attachments immediately; Sonarr's `mediaInfo` lacks bit depth, so the probe is not optional.

**Playback decision engine.** Keep Jellyfin's architecture (server-authoritative, decision computed from a profile the client posts per playback) and fix its two weaknesses. First, version the profile schema and drop the DLNA vocabulary (`DidlMode`, `DlnaProfileType`, `EnableMpegtsM2TsMode`); express capabilities as direct-play tuples (container × video codec × audio codec), per-codec predicates (width, height, bitrate, bit depth, level, frame rate, range type, channels), transcode targets (protocol, container, codecs, max channels), and a **first-class subtitle-delivery axis per format**: `Native` (client renders with libass and will fetch attachments), `Sidecar` (raw file), `HlsText` (WebVTT segments, never for ASS), `Embed` (remux into MKV), `Burn`. Second, return the reasons: every response should list, per media source, the ordered rule evaluations and the reason each cheaper method was rejected, which is the diagnostic Plex buries in debug logs and Jellyfin exposes only as a flag set ([Plex forums: always transcoding](https://forums.plex.tv/t/media-server-always-transcoding/787669.md); [StreamBuilder.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Model/Dlna/StreamBuilder.cs)). Do not build a server-side profile registry keyed by User-Agent; Plex's rotted into "generic player" fallbacks and an NDA'd header DSL ([Plex forums: client profiles](https://forums.plex.tv/t/client-profiles-still-relevant/849312)). Do add a server-wide and per-user policy for "burn when transcoding" and "burn complex ASS," since Jellyfin and Plex both make that a per-client setting with no default ([forum](https://forum.jellyfin.org/t-enable-always-burn-in-subtitle-when-transcoding-by-default); [Plex forum](https://forums.plex.tv/t/subtitles-only-image-formats-as-server-default/163393)). Treat `Transcode` with video stream copy plus audio transcode and sidecar ASS as a distinct, cheap path so an ExoPlayer client with libass can still avoid the video encode when only audio is incompatible; this is exactly the case Plex staff said they were "working on" in 2021 and never shipped ([Plex forums](https://forums.plex.tv/t/embedded-subtitles-ass-forces-transcoding-with-certain-clients/706266.md)).

**Transcoding pipeline.** Copy Jellyfin's HLS design because it is the right one: synthesize the full VOD playlist from runtime or keyframes before encoding, serve segments lazily, restart a single ffmpeg at `segmentId × SegmentLength` on seeks with `-copyts -avoid_negative_ts disabled`, garbage-collect on a ping timeout, and prefer fMP4 segments with `movflags=+frag_discont+skip_sidx` so HEVC/AV1 and Opus/FLAC survive the container ([DynamicHlsController.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/DynamicHlsController.cs)). Build the filter graph the way `EncodingHelper` does, per vendor, and for ASS burn-in use the `alphasrc` + `subtitles=…:alpha=1:fontsdir=<attachments>` + `hwupload` + `overlay_*` chain so the video stays on the GPU; pass `original_size` so font scaling survives resolution changes, an issue the notes flag as plausible but unbenchmarked ([MLT avfilter.subtitles reference](https://www.mltframework.org/plugins/FilterAvfilter-subtitles/)). Because libass rasterization stays on the CPU, add an admission controller that caps concurrent burn-in jobs separately from concurrent GPU encodes and reports it in the dashboard. Ship a fonts volume with Noto CJK by default and document it; Jellyfin's refusal to ship fonts is the single most common cause of box-glyph complaints ([jellyfin #14708](https://github.com/jellyfin/jellyfin/issues/14708)). Extract embedded subtitles with `-c:s copy` into a cache with freshness metadata, exactly as `SubtitleEncoder` does, and never convert SSA to ASS or either to VTT ([SubtitleEncoder.cs](https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.MediaEncoding/Subtitles/SubtitleEncoder.cs)).

**Auth and sessions.** Local accounts with per-device opaque tokens (revocation is deleting the device row), a device-code flow identical in UX to Quick Connect, managed child profiles that are PIN-switchable, library-scoped sharing, and optional OIDC federation that is never required for LAN or WAN playback. Keep sessions in memory with a 5-minute idle stop and a websocket for library and user-data pushes, as Jellyfin does, because clients re-report and persistence buys nothing ([SessionManager.cs](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Session/SessionManager.cs)).

## Client stacks per platform: Media3 plus ass-media, libmpv as the hedge, jassub on web

**Android TV** has two viable stacks in 2026, and the pragmatic design is to ship both behind a per-file engine choice, which Wholphin and Findroid arrived at independently ([Wholphin README](https://github.com/damontecres/Wholphin); [Findroid README](https://raw.githubusercontent.com/jarnedemeulemeester/findroid/main/README.md)). The default engine is Media3/ExoPlayer with `io.github.peerless2012:ass-media` (libass-android's `lib_ass_media` extension, MIT, v0.5.1 on 11 August 2026), which keeps Google's MediaCodec and tunneled playback, Leanback or Compose-for-TV focus handling, HDR passthrough and the official `jellyfin-sdk-kotlin`, and adds libass as an OpenGL overlay ([libass-android](https://github.com/peerless2012/libass-android); [GitHub API releases](https://api.github.com/repos/peerless2012/libass-android/releases/latest)). Its known caveats are concrete: render timing does not align with video frame timing (an androidx/media limitation, "probably still not fully correct"), complex typesetting or 4K output can exceed one frame in OVERLAY mode so use OPEN_GL mode, the glyph cache defaults needed raising (a Shield test went from 1,024 to 10,000 glyphs with 128 MB, and 256 MB was suggested for 4K), the Media3 1.9.0 attachment bug (androidx/media#2536) affected font loading, and no source confirms whether `ass-media` parses MKV font attachments at all, so the Roxy TV app must fetch fonts explicitly from the server's attachments endpoint and hand them to libass ([libass-android #57](https://github.com/peerless2012/libass-android/issues/57); [PR #5397 discussion](https://github.com/jellyfin/jellyfin-androidtv/pull/5397)). A Flutter-side note applies equally to Kotlin: "libass on Android can't find system fonts, so fonts must be bundled as assets and referenced by family name" ([flutter_ass_player](https://pub.dev/packages/flutter_ass_player)). The second engine is embedded libmpv with `hwdec=mediacodec`, using mpv-android's `MPVLib` and `MPVView` as reference code (the maintainers state it "is not a library/module (AAR) you can import") or jarnedemeulemeester's `libmpv-android` ([mpv-android](https://api.github.com/repos/mpv-android/mpv-android); [libmpv-android](https://github.com/jarnedemeulemeester/libmpv-android)). mpv gives the best ASS fidelity and reads MKV attachments natively, but you then own hwdec quirks per SoC, HDR and Dolby Vision handling, audio passthrough, and a 20–40 MB native payload, and the device reports are mixed: "On the Nvidia Shield the MPV backend doesn't really work, it has an issue with stuttering" versus a Shield Pro that "direct-plays just fine" ([Plex forum](https://forums.plex.tv/t/ass-subtitle-delay-on-nvidia-shield/842886); [Emby community](https://emby.media/community/topic/123551-ass-subtitles-causes-stuttering)). No benchmark of either stack on Shield, Google TV Streamer or Fire TV exists, so plan a device test matrix and a per-device fallback to server burn-in. For hardware, the Shield TV Pro remains the strongest CPU/GPU for 4K libass compositing and the only box with lossless passthrough, while the Onn 4K Pro is the best value with AV1 and HDR10+ but no TrueHD/DTS ([JellyWatch device comparison](https://jellywatch.app/blog/best-streaming-device-jellyfin-4k-hdr-av1-2026); [XDA on Onn 4K Pro](https://www.xda-developers.com/the-60-onn-4k-pro-does-all-the-things-i-kept-my-nvidia-shield-around-for/)).

**Web** should use jassub, not libass-wasm. jellyfin-web uses `@jellyfin/libass-wasm` 4.2.4, its fork of JavascriptSubtitlesOctopus, after adopting jassub and migrating back in March 2024 because jassub "doesn't work in legacy browsers"; upstream JavascriptSubtitlesOctopus has not been pushed since September 2024, whereas jassub (TypeScript, MIT, "Supports all SSA/ASS features," WebGL-accelerated, async, with embedded-font support) was pushed on 10 October 2026 ([jellyfin-web jassub history](https://api.github.com/search/issues?q=repo:jellyfin/jellyfin-web+jassub&sort=updated); [GitHub API: JavascriptSubtitlesOctopus](https://api.github.com/repos/libass/JavascriptSubtitlesOctopus); [GitHub API: jassub](https://api.github.com/repos/ThaUnknown/jassub)). A greenfield client can decline legacy-browser support, but if Tizen or webOS TV browsers are targets, test jassub's WebAssembly and OffscreenCanvas requirements first, because that is exactly where Jellyfin got burned. Serve fonts from the attachments endpoint plus a fallback-font list, and cap total fallback-font size; a Jellyfin member warned that fallback fonts over 20 MB break web rendering ([jellyfin-web #6299](https://github.com/jellyfin/jellyfin-web/issues/6299)).

**Apple TV** is second-tier and higher-maintenance. AVPlayer burns in; libass-grade rendering requires VLCKit/SwiftVLC (Swiftfin's path, at the cost of HDR, Dolby Vision and Atmos handling per user reports) or a libmpv build via MPVKit, whose README says it is "only suitable for learning libmpv" and "will not be maintained too frequently" ([Swiftfin #1892](https://github.com/jellyfin/Swiftfin/issues/1892); [MPVKit](https://github.com/mpvkit/MPVKit)). Infuse renders authored ASS with its own engine but cannot override styles, has no custom font folder, and regressed on external-file fonts in August 2026 ([Firecore: Infuse 8.5 bug](https://community.firecore.com/t/bug-external-ass-subtitles-ignoring-embedded-mkv-fonts-in-infuse-8-5/60462)). **Roku, webOS and Tizen** cannot be made libass-correct on device: Roku cannot direct-play ASS and it is "unknown whether Roku renders a muxed ASS track at all," and the TV platforms' native players force burn-in ([jellyrock #1008](https://github.com/jellyrock/jellyrock/issues/1008); [jellyfin-tizen #103](https://github.com/jellyfin/jellyfin-tizen/issues/103)). Server-side libass burn-in therefore stays a first-class, non-optional transcode mode regardless of which path you pick.

## Phased plan: client first, server only if OIDC or control forces it

The effort figures below are my estimates inferred from repository timelines; no primary source publishes developer-months for any of these projects.

**Phase 0 (days): fix what you have.** Upgrade to Jellyfin 12.2, mount a fonts folder with Noto CJK into the server container, prefer releases with fonts and ASS muxed into the MKV, pre-extract subtitles and attachments (the official Subtitle Extract plugin, or play once from web) so burn-in uses the right fonts, and on the living-room TV install either Wholphin, Kodi with Jellyfin for Kodi, or the 0.20.0-beta with the developer libass toggle; set "always burn in when transcoding" where the client offers it ([jellyfin-androidtv #3854](https://github.com/jellyfin/jellyfin-androidtv/issues/3854); [jellyfin-plugin-subtitleextract](https://github.com/jellyfin/jellyfin-plugin-subtitleextract/releases); [v0.20.0-beta.1](https://github.com/jellyfin/jellyfin-androidtv/releases/tag/v0.20.0-beta.1)). This immediately gets you direct-played HEVC Main10 with full typesetting on Android TV and leaves Sonarr, Radarr and the download client untouched.

**Phase 1 (one experienced Android developer, roughly 3–6 months to a usable beta): the Roxy TV app, the Android TV client.** Kotlin, `jellyfin-sdk-kotlin`, Compose for TV, Media3 1.11 plus `ass-media` in OpenGL mode with raised glyph cache, explicit font fetching from `/Videos/{id}/{mediaSourceId}/Attachments/{index}`, a `DeviceProfile` that lists `ass`/`ssa` as `External` so the server never burns in, an optional libmpv engine for files the Media3 path struggles with, per-user accounts via `AuthenticateByName` and Quick Connect, and the standard `Sessions/Playing` reporting loop. Wholphin's trajectory (created September 2025, Play Store and about 3,000 stars by October 2026) is the reference for what one focused developer can do on this exact scope ([GitHub API: Wholphin](https://api.github.com/repos/damontecres/Wholphin)). Risks: `ass-media` is a single-maintainer project the official app had to pull from a release once; Media3 frame-timing alignment remains open; Jellyfin's API churns at major versions (12.0 removed legacy prefixes and the deprecated sign-in) ([PR #5032](https://api.github.com/repos/jellyfin/jellyfin-androidtv/pulls/5032); [Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/)).

**Phase 2 (similar scale): Roxy Web** with jassub, HLS.js, and the same profile discipline, scoped tightly; Jellyfin-Vue has been in progress for years, so feature creep is the main risk ([GitHub API: jellyfin-vue](https://api.github.com/repos/jellyfin/jellyfin-vue)). Add an Android mobile variant of the Roxy TV app afterwards; the official mobile libass port is promised but unscheduled.

**Phase 3 (only if needed; multi-year for a small team): Roxy Server.** Build the Go design above behind a Jellyfin-compatible shim so Sonarr, Radarr, the Roxy TV app and Roxy Web move over without change, starting with the scanner and the compat endpoints, then probing and the decision engine, then HLS transcoding with burn-in, then auth and OIDC. Kyoo's history is the calibration point: started in 2019, rewritten for v5 in 2026, still one maintainer, Android TV requested December 2023 and first merged September 2026 ([Kyoo README](https://raw.githubusercontent.com/zoriya/Kyoo/master/README.md); [Kyoo Android TV issues](https://api.github.com/search/issues?q=repo:zoriya/Kyoo+%22android+tv%22&sort=updated)). The honest list of what Roxy Server buys that Jellyfin does not: native OIDC and device-code login for TV apps, a webhook-and-ID-driven scanner instead of filename regexes, server-wide subtitle policy, explainable decisions, eager attachment extraction, and first-class absolute/AniDB ordering. The honest list of what it does not buy: any improvement in ASS rendering on Android TV, Android mobile, Apple TV, Roku, webOS or Tizen, because libass on those devices is the client's job. Forking Jellyfin instead of rewriting gets you OIDC and the scanner changes for a fraction of the cost but commits you to merging upstream security fixes (12.0 and 12.2 shipped them) indefinitely ([jellyfin releases](https://github.com/jellyfin/jellyfin/releases)).

The counter-argument deserves to be stated plainly: building only the Roxy TV app and Roxy Web on Jellyfin's API captures most of the benefit. The server already classifies ASS correctly, serves the ASS track and fonts to any client that asks, and burns in with libass otherwise; its remaining defects (lazy attachment extraction, no shipped fonts, per-client burn-in settings, no OIDC) are all workable with configuration or a small plugin, and none of them is the reason your TV shows unstyled or transcoded subtitles. Every project with real users in this space is a client, and the only active server alternative has no TV client after three years. If, after Phase 1 and 2 are in daily use, you still want OIDC, server-wide subtitle policy or a Sonarr-driven scanner, Phase 3 is a well-defined project with a known contract; starting there is the one ordering the evidence argues against.

## Conclusion

The research reframes the question from "can a better media server be built" to "which layer is actually broken," and the answer is unambiguous: the server layer works, and the client layer on Android TV and mobile is what fails. That reframing changes the economics completely. A server rewrite is a multi-year project that reproduces a probe-decide-transcode-session-auth stack and a Jellyfin-compatible integration contract while leaving the subtitle problem exactly where it was; a client costs months, inherits arr compatibility for free, and attacks the problem directly with libass-android or libmpv. The two most consequential technical facts for the client build are that Google will not merge libass into Media3, so the third-party overlay path and its frame-timing caveats are permanent, and that font attachments must be fetched and fed to libass explicitly because no Android stack except Kodi documents doing it for you.

Two things could change the recommendation. If Jellyfin 0.20.0 ships stable with the libass toggle enabled by default and the timing issues resolved, even the client build loses urgency and the project collapses to configuration. If instead you find yourself fighting Jellyfin's scanner over absolute numbering, needing OIDC for a multi-household deployment, or wanting burn-in policy enforced server-wide, the Roxy Server design in this report is the one to build, with its Jellyfin-compatible shim ensuring the pipeline from Sonarr and Radarr to the download client to storage never notices the swap. Either way, the ordering is the same: client first, then decide.
